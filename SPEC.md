## Phase 6 — SOLID & Design Patterns
- [x] SOLID audit with before/after refactors documented in `docs/solid.md` — audit in `docs/solid.md`; the LSP/ISP finding it turned up (bare `ValueError` as the universal auth failure signal) fixed by routing auth failures through domain exceptions (PR #25)
- [x] Factory pattern: `StorageFactory` returning S3/local/memory backends via `Protocol` — `StorageBackend` protocol in `src/storage/base.py` with no boto3, filesystem or settings import; `S3Storage`/`LocalStorage`/`MemoryStorage` implement it structurally and one parametrised contract suite runs against all three. Presigned URLs are deliberately left off the protocol — only S3 can mint them, so putting them there would trade an OCP violation for an LSP one — and stay on `S3Storage`, which is why `/api/v1/uploads` is unchanged. Closes finding 5 of `docs/solid.md` (PR #26)
- [x] Strategy pattern: pluggable `NotificationStrategy` chosen per user preference — `NotificationStrategy` protocol in `src/notifications/base.py` over `Notification`/`Recipient`/`NotificationResult`, free of SQLAlchemy, httpx and settings; `email`, `webhook` and `none` implement it structurally and one parametrised contract suite runs against all three. `Recipient` is deliberately not the `User` row — `recipient_from_user` is the only code aware of both, so a webhook body can never be assembled from an object carrying the password hash. The channel comes from `users.notification_channel` (migration 0003): a plain string rather than an enum, so adding a channel stays a `register` call instead of a migration plus a deploy-order problem; unknown values raise rather than silently defaulting, empty ones fall back. Webhook deliveries are HMAC-signed over `{timestamp}.{body}` so a capture cannot be replayed by rewriting the header, and user-supplied URLs are SSRF-checked — the one gap, a hostname that resolves privately, is documented and asserted by a test rather than implied away (PR #27)
- [x] Decorator pattern: `@cached`, `@retry`, `@timed` decorators preserving signatures via `ParamSpec` — in `src/decorators`, documented in `docs/decorators.md`, 100% line coverage. Signatures survive both halves of the round trip: a `ParamSpec` on every `__call__` for mypy, `functools.update_wrapper` for `inspect.signature`, which is how FastAPI builds a route's parameters. Each is a factory that must be called (`@timed()`, not `@timed`) — the bare form needs an implementation signature loose enough to take a function or nothing, which erases the `ParamSpec` link. `@retry` re-raises the original exception rather than a `RetryError`, because this API derives status codes from exception types and a wrapper would turn a 409 into a 500 on the third attempt; it also refuses to retry `CancelledError` even under `on=BaseException`, and checks exhaustion before `should_retry` so caller code is never run for a decision that no longer exists. `@cached` collapses concurrent misses behind a refcounted per-key lock and never caches a failure; it is per-process, and the docs say so before they say anything else. Two bugs the composition tests found were fixed rather than documented around: `@retry` over `@cached` took the sync branch and silently retried nothing (an `AsyncCachedFunction` is a callable object, not a coroutine function), and decorating a `functools.partial` raised `AttributeError` for a missing `__qualname__` (PR #28)
- [x] Observer pattern: async domain event bus with typed subscribers — `src/events`, documented in `docs/events.md`, 100% line coverage. `subscribe(event_type, handler)` is checked by mypy in both directions, and dispatch walks the MRO, so an audit log subscribing to `UserEvent` is an ordinary subscriber rather than a special case in `publish`. `publish` awaits its subscribers: `create_task` would drop exceptions nothing holds and outlive the request scope whose context it borrowed, so work that should not be paid for inline is enqueued to Celery from *inside* a subscriber. Subscribers run concurrently and fail independently — a broken mail queue cannot fail a registration that already committed — while cancellation propagates rather than being recorded as eight spurious failures, and a handler that merely overran its `timeout` is a failure. Every publish in `AuthService` sits after the commit so nothing reacts to a transaction that then rolls back, and nested publishes are counted in a `ContextVar` because a cycle here is a request that never returns. Subscribers are registered from the lifespan, not at import, so importing a module never starts sending mail. Two bugs the tests found were fixed rather than documented around: a `Subscription` compared field-wise, letting one from a *different* bus unsubscribe a local handler (identity handles now), and structlog reserves the `event` kwarg, so every publish raised `TypeError` until the log keys became `event_name`. The bus is in-process and forgets; the transactional outbox in Phase 7 is the durable answer (PR #29)
- [x] Adapter pattern: `PaymentGateway` protocol with two concrete adapters — `PaymentGateway` protocol in `src/payments/base.py`, free of httpx, any provider SDK and settings; `StripeGateway` and `PayPalGateway` translate it to two APIs that agree on almost nothing (form encoding vs JSON, integer minor units vs decimal strings, a static key vs a cached OAuth2 token, `Idempotency-Key` vs `PayPal-Request-Id`, a 402 `card_error` vs a 422 `INSTRUMENT_DECLINED`), and one parametrised contract suite runs against both. This is the adapter pattern rather than another strategy: the two are not one idea implemented twice but existing APIs this codebase does not control, so translation *is* the work. `Money` is integer minor units plus a currency-exponent table and refuses an unlisted currency rather than defaulting to two decimals — the default is wrong in both directions at once, turning the same ¥1000 into ¥10 at Stripe and ¥100,000 at PayPal. A decline is a 402 distinct from the 503 that means retry is safe, and the reverse mistake is tested too, since reporting our own malformed request as a declined card sends shoppers to their bank over our bug. PayPal's `charge` returns the *capture* id, not the order id the response leads with, because only a capture can be refunded — an order id would work all the way through checkout and fail at the first refund — and capture status wins over order status, an order reading COMPLETED while its capture is still PENDING being the difference between money that exists and money that does not. `ChargeRequest.reference` is required rather than optional because an optional idempotency key is one nobody passes. No retry or circuit breaker (Phase 9 owns that; the idempotency keys are what make adding it safe), no vaulting/subscriptions/webhook verification on the protocol (Stripe HMACs the raw body, PayPal fetches a certificate chain — adapter-specific, as presigned URLs are on `S3Storage`), and no route, which is the next item (PR #30)
- [x] Dependency inversion via FastAPI `Depends` + protocol-typed providers, overridable in tests — `AuthService` now takes four protocols (`UserStore`, `RefreshTokenStore`, `UnitOfWork`, `EventPublisher`) instead of building `UserRepository(db)` and holding a whole `AsyncSession` for two methods, which closes findings 4 (DIP) and 6 (ISP) of `docs/solid.md` — the same seam, cut once. `src/dependencies.py` is the composition root: every provider is annotated with the protocol and returns the implementation, so mypy fails the build the day one drifts, and the concrete names appear nowhere else in the request path — `src/auth/router.py` no longer imports `get_db` at all. `Depends` alone injects without inverting; the protocols are what make the substitution possible. There is no unit-of-work adapter class because `AsyncSession` already satisfies `UnitOfWork` structurally, and no `rollback` on it because nothing calls one. `EventPublisher.publish` returns `object` rather than `PublishResult`, since every caller here discards it on purpose. The three DB-backed providers each take the session through `Depends(get_db)`, which FastAPI caches per request: load-bearing rather than an optimisation, since three sessions would have the unit of work committing a transaction the repositories never wrote to, and a registration answering 201 while persisting nothing. The protocols still name the SQLAlchemy models, a bounded compromise documented in place — the cost of a concrete model is that a fake must construct one, where the cost of a concrete repository was that a fake had to *be* a session. `tests/fakes.py` is the payoff: the auth, OAuth and event suites now run the real service over in-memory stores, seeded by what exists rather than by the order the service happens to query in — the stub they replaced answered `execute()` from a `side_effect` list, so adding a lookup shifted every later answer onto the wrong question in silence. A fitness function parses the imports of `src/auth/service.py` and `src/auth/router.py`, so the one-line regression that reintroduces finding 4 fails a test instead of passing review. No payments route: charging a card needs the `Idempotency-Key` middleware that opens Phase 7, and a charge endpoint that dedupes nothing turns a retried request into a second charge — `PaymentGatewayDep` is wired and waiting for it. Documented in `docs/dependency-injection.md` (PR #31)

## Phase 7 — Concurrency & Data Integrity
- [x] Idempotency middleware: `Idempotency-Key` + Redis dedupe with response replay — `IdempotencyStore` protocol in `src/idempotency/base.py` with Redis and in-memory backends behind one contract suite, and the ASGI middleware in `src/middleware/idempotency.py`; documented in `docs/idempotency.md`, 100% line coverage on every new module bar the protocol stubs. Middleware rather than a dependency because a dependency runs inside the route — it can see the request but not the response, and the response is what has to be replayed — and cannot cover the endpoint someone forgets to decorate, which is the one that will double-charge. Redis's `SET NX EX` is the reservation: a `get`-then-`set` pair lets two simultaneous retries both find nothing and both execute, so the contract suite measures that with 20 concurrent reservations against a real server rather than asserting it. Two TTLs, because one value cannot be both — a reservation expires in 60s so a worker killed mid-request cannot answer its own retries with 409 for a day, while a completed record lives 24h, which is a question about the client's retry window. Keys are namespaced by `sha256(Authorization)`: keys are client-chosen, so two callers will eventually pick the same one and the second would otherwise be handed the first's response. 5xx, 408, 425 and 429 release the reservation instead of being stored, since pinning a transient failure to a key answers the retry it invites with the very error being retried; an exception releases it too, `CancelledError` included. `Set-Cookie` is stripped from stored responses. Reuse is checked before in-progress so a client bug is a 422 rather than 409 or 422 depending on timing, and the store failing is a 503 by default because serving the request anyway is the double execution the caller asked to be protected from. Added *before* `RequestIDMiddleware` so it runs inside it: idempotency logs carry the replaying request's id and a replay is stamped with a fresh `X-Request-ID`, asserted from outside. `render_app_exception` was split out of `app_exception_handler` because exception handlers are installed inside the middleware stack, so a short-circuit never reaches them and would otherwise grow a second error envelope. No route requires a key yet — that is a per-route dependency, not middleware policy — and idempotency is not a transaction: a handler that commits and then dies before the response is stored still re-executes, which the transactional outbox later in this phase is the durable answer to (PR #32)
- [x] Optimistic concurrency: SQLAlchemy `version_id_col` + `If-Match`/ETag, 412 on conflict — `src/concurrency` holds the HTTP half (`EntityTag`, `IfMatch`, `resource_version_tag`, free of SQLAlchemy), `User.__mapper_args__["version_id_col"]` the storage half, and `/api/v1/users/me` is where they meet; documented in `docs/optimistic-concurrency.md`, 100% line coverage on every new module. The precondition is checked twice deliberately: `require_match` is the check that fires in practice and is the only one that can name the current tag, while the `WHERE version = :loaded` SQLAlchemy appends is the one that is *sound* — between the comparison and the write there is a window only the database can adjudicate, and keeping just the first leaves a lost-update race no test issuing one request at a time would ever reveal. `If-Match` uses strong comparison (RFC 9110 §13.1.1), so `W/"…"` never satisfies it; a comma is a legal `etagc`, so the header is scanned against the grammar rather than split on commas; an unparseable precondition is a 400 rather than a silent pass, because ignoring it switches the protection off exactly when the client believed it was on; a missing one is 428 rather than a blind overwrite. The tag carries the row id as well as the version — every row is at version 1 when created and `/users/me` is one URI naming a different row per bearer token, so a bare `"1"` from one client would compare equal to someone else's row — and those responses are `Cache-Control: private, no-store` for the same reason. 412 is kept distinct from 409: one means re-read and retry, the other means repeating the request fails identically. `tests/test_optimistic_concurrency_db.py` runs two real transactions at one row against the CI Postgres (skipped only when `DATABASE_URL` is unreachable, as the Redis leg of the idempotency contract suite is) and found a real bug while being written: logging `user.version` inside the `StaleDataError` handler reloaded an expired attribute through the session the failed flush had already killed, turning the 412 into a 500. No `If-None-Match`/304 — that is a caching question, not a correctness one — and no decorator wrapping the pattern, since *which* tag is current differs per resource and a wrong guess fails open (PR #33)
- [x] Pessimistic locking with `with_for_update()` and a deadlock-retry wrapper — `src/locking` holds the two halves that are only useful together: `rows` takes the locks (`lock_row`, `lock_rows`, `lock_timeout`, and a `LockMode` enum over all four Postgres row locks) and `retry` re-runs a transaction Postgres killed to break a deadlock. Documented in `docs/pessimistic-locking.md`, 100% line coverage on all four new modules. **The retry cannot be `@retry` from `src/decorators`, and not for stylistic reasons:** a Postgres transaction is dead after any error, so re-running a statement inside it does not reproduce the deadlock — it raises 25P02, and attempt three would raise it again. The retry is only sound with a `ROLLBACK` between attempts, which a general-purpose call retrier has no business knowing about; the backoff *policy* is not duplicated, since `backoff_delay` moved to `src/decorators/base.py` and both loops call it. **A lock over a stale in-memory copy protects nothing, and the ORM hands you one by default** — a `SELECT ... FOR UPDATE` for a row the session already holds takes the lock and returns the *cached* instance, because the identity map wins over the result set, so the caller decides against values read before the lock existed. That is the race the lock was for, failing silently in code that looks correct; both functions run `populate_existing=True` through one shared helper, and a test demonstrates the broken form rather than describing it. `Session.get(..., with_for_update=...)` is the obvious alternative and is refused: it routes through the refresh path, which turns on version checking, so a pessimistic reader of a row carrying the item-2 `version_id_col` gets `StaleDataError` instead of the current row it asked for. Classification is by SQLSTATE and never by exception class, since SQLAlchemy returns `DBAPIError` for a deadlock, a lock timeout and a unique violation alike under asyncpg; 55P03 is deliberately not retryable, because it is what `nowait` and `lock_timeout` raise and a retry loop is exactly the queue the caller refused. The CI Postgres 17 service log records the real `deadlock detected`, the `canceling statement due to lock timeout` and the `division by zero` → `current transaction is aborted` pair, so none of these tests silently skipped. No route consumes it: nothing in the schema has a balance, a stock count or a queue, and a lock on a route that does not need one is a worked example pretending to be a requirement — the transactional outbox later in this phase is the first genuine consumer, claiming rows with the `FOR UPDATE SKIP LOCKED` batch pattern. No advisory locks (`pg_advisory_xact_lock` is a different idea; the Redis item next door covers the cross-process case) and no `of=` on the lock clause (PR #34)
- [x] Distributed lock via Redis with fencing tokens, exposed as an async context manager — `src/distributed_lock`, documented in `docs/distributed-locking.md`, 100% line coverage on the context manager, the in-memory backend and the factory, 99% on the Redis one. **The token is the feature and the lock is the optimisation**, which is the opposite of how these are usually built: every acquisition is a lease, because a lock without one is held forever by any worker that dies inside it, and the price of that guarantee is that a lease can expire while its holder still believes it holds one — a GC pause, a blocked event loop, a partition, and the holder finds out late or never. Renewal narrows that window and cannot close it, since the pause can land between the last renewal and the write; no lock server closes it either, Redlock included, because a quorum still cannot bound a client's pause. So each acquisition mints a strictly increasing, never-reused token and the *resource* refuses anything lower (`WHERE fence < :token`, or `require_fence` where the resource is not a row), which is why `Lease.token` is part of the protocol rather than a detail of the Redis encoding. The fence counter therefore has no TTL and **must not be evictable** — if it goes, the next `INCR` returns 1 and the check silently stops rejecting the writers it exists to reject, so `maxmemory-policy` must not be an `allkeys-*` policy, and an async failover replays tokens for the same reason, stated in the docs rather than implied away. Every operation is one Lua script: a `get`-then-`set` acquire lets two workers into the same section, measured with 20 concurrent acquisitions against the real server rather than asserted. Release compares before deleting, since a bare `DEL` after your lease expired frees whoever came next and a third caller walks into the section they are still running — hence three release outcomes rather than a bool. The token is stable across renewals, because it identifies the lease and not the renewal, and bumping it would fence a holder out of its own earlier writes. A lease the store reports gone raises `LockLostError` on a clean exit — reporting success for work that may have been fenced out is worse than a 409 — but never over the body's own exception, and never for a release the store simply did not answer, which is no evidence the lease had ended. Not reentrant: a second lease for one owner would let an inner block's release free the outer block's lock. `wait_timeout` defaults to 0, mirroring `nowait` in `src/locking/rows.py` (a retry loop is a queue), and the wait reuses `backoff_delay` from `src/decorators/base.py` rather than adding a third backoff policy. No fail-open switch, unlike `IDEMPOTENCY_FAIL_OPEN`: running a section whose coordination is unreachable is the concurrent execution the lock was taken to prevent. No route consumes it — nothing here needs cross-process exclusion yet, and a lock on a route that does not need one is a worked example pretending to be a requirement — so `LockBackendDep` is wired and waiting for the transactional outbox later in this phase (PR #35)
- [x] GIL-bound work offloaded to `ProcessPoolExecutor`; IO-bound to `asyncio.gather` with semaphores — `src/parallel`, documented in `docs/parallel-execution.md`, 100% line coverage on all five new modules. Two problems that look alike and have opposite fixes: a handler *waiting* on IO leaves the loop thread idle, so overlap the waits; a handler *computing* holds it, so overlapping buys nothing — and neither does a thread, since the GIL means a compute-bound thread takes the interpreter away from the loop exactly as a coroutine does. `run_in_threadpool` is right for blocking calls that release the GIL (a sync driver, `open()`, argon2) and wrong for compute, which is why the CPU half exists at all. **`fork` is refused rather than discouraged:** a forked child of this process inherits the SQLAlchemy pool's open sockets, the Redis client's and the loop's epoll set, and two writers on one Postgres connection do not fail cleanly — they interleave protocol frames and return one request's rows to another; `fork` with threads is undefined at the POSIX level besides, and uvicorn runs threads, so `Settings` types the field `Literal["spawn", "forkserver"]` and fails at start-up rather than at the first offload. **The deadline is armed inside the worker with `setitimer`**, because `asyncio.wait_for` around an executor future cancels the wait and never the work — a runaway call would hold its slot forever while the parent politely reported a timeout, and a few of those leave the pool with no capacity and nothing in the log. `WorkerDeadline` derives from `BaseException` so an ordinary `except Exception:` in the workload cannot swallow it, measured against a workload that tries rather than asserted. There is deliberately no parent-side timer racing it: a wait measured from submission includes queue time, so under load it would fire first and report a timeout for a call that had not started — `timeout` is a budget for the call, and queue time is bounded separately by admission control. The two limits are stated rather than papered over (no `setitimer` on Windows; a C extension holding the GIL never reaches the bytecode boundary a handler needs), and `spin_with_alarm_blocked` reproduces the second deterministically so the fallback path runs in CI instead of for the first time in a deployment. **Admission control replaces an unbounded queue** — `ProcessPoolExecutor` queues without limit and queued submissions sit in the *parent's* memory as pickled payloads, so past `workers * (1 + depth)` calls get a 503 rather than growing the heap under a spike whose clients have already given up — and a `BrokenProcessPool`, which is terminal for an executor, is recovered by replacing it, since otherwise one OOM kill takes the endpoint down until the pod restarts. On the IO side, the two things wrong with plain `asyncio.gather` are asserted against `asyncio` itself in `TestTheProblemBeingSolved`, so the justification fails the build if it ever stops being true: it is unbounded, and with `return_exceptions=False` it propagates the first exception while leaving the siblings running, so a handler that fans out five calls and returns 502 leaves four in flight holding connections. `gather_bounded` caps concurrency and cancels the rest *and awaits them* — the awaiting is load-bearing, since `cancel()` only schedules a `CancelledError` and the coroutine must be resumed for its `finally` to run — takes factories rather than coroutines so awaitables are built one per slot, and returns input order. `run` keeps a pure `ParamSpec` and the deadline rides on `with_timeout(...)`, the same shape as `DeadlockRetryPolicy` and for the same reason: a `ParamSpec` cannot carry parameters after `*args`, so a `timeout=` keyword would have cost call-site argument checking. No route consumes either half — what to offload and how long to allow it are properties of the work, and a demo endpoint would be a worked example pretending to be a requirement — so `CpuPoolDep` is wired and waiting. The semaphore bounds concurrency and not rate; an upstream that publishes a rate needs a token bucket as well (PR #36)
- [x] Immutability: frozen Pydantic models, `Final`, and frozen dataclasses for value objects — `FrozenDict` in `src/immutable.py`, documented in `docs/immutability.md`, 100% line coverage. Each of Python's three tools guards exactly one edge, and this codebase was relying on them for a guarantee none of them gives. **`Final` is about the name, not the object:** twelve `Final` names held a writable dict and `__all__` held a writable list, so `CURRENCY_EXPONENTS["JPY"] = 2` type-checked, ran, and would have converted yen wrongly for the life of the process. The registry defaults were the sharpest of them, since each registry's `reset()` rebuilds from `dict(DEFAULT_*)` — one write to the constant poisons the escape hatch itself, permanently and for every test that runs afterwards. **`frozen=True` is about the attribute, and it does not copy:** `ChargeRequest(..., metadata=d)` stayed aliased to the caller's `d`, and both payment adapters send `metadata` upstream, so an edit between construction and the HTTP call reaches the provider's records while the request that was validated says something else; `Notification` has the same shape with delivery asynchronous, so "what the caller's dict says now" is not what it said when the notification was built. **Pydantic adds a third gap:** validation replaces the container, so a frozen model holds a dict it built. `FrozenDict` closes all three by copying on construction and exposing no mutator. It is not a `dict` subclass — that inherits six mutators each needing an override, and `dict.update` in C does not route through `__setitem__` anyway. It is hashable, which a frozen dataclass with a plain-dict field is not, so such a value object could not be a set member or an argument to a `@cached` function. It is picklable, which `MappingProxyType` is not, and `Notification` goes onto a Celery queue while `src/parallel` pickles arguments into worker processes. One Pydantic core schema wrapping Pydantic's own dict schema lets the same type serve module constants, dataclass fields and model fields with the OpenAPI document unchanged. `Settings` is frozen for a load-bearing reason rather than a tidy one: `get_strategy` is `@cache`d, the storage and payment registries build from a `Settings` at first use, and the idempotency and lock backends are built once in the lifespan, so a write to the singleton used to take effect for whatever had not been built yet and nothing else — the worst failure shape available, since every individual piece behaves exactly as designed. `CursorPage.items` is a tuple and `PresignedUploadResponse.fields` a `FrozenDict`, because a frozen model with a mutable container field is frozen in name only and the S3 POST policy signs those fields. `tests/test_immutability_gate.py` walks every module under `src/` and fails on a mutable `Final` constant, an unfrozen dataclass or an unfrozen model, with exemption tables that require a written reason and reject both a stale entry and an empty one — it found three constants a manual pass had missed. Two exemptions are recorded, the cache entry and the in-memory lock's held-lease record, both state rather than values. Deep immutability is deliberately not claimed: `FrozenDict[str, list[int]]` still hands out the same lists, and `hash()` is what complains (PR #37)
- [x] Transactional outbox: event row in the same session, async relay publisher — `src/outbox`, migration `0005`, documented in `docs/outbox.md`, 100% line coverage on every new module bar the protocol stubs. An event and the change that caused it are two systems with no transaction between them, and the codebase had already picked its poison: `AuthService` published *after* `uow.commit()` so nothing could react to a rolled-back transaction, at the price of losing the reaction outright if the process died in the gap. Moving the call does not close that gap, it swaps which half can happen alone — so publishing now writes a **row** in the caller's own session, and `OutboxPublisher` being an `EventPublisher` means every producer keeps its one-line call. **The ordering rule inverts as a result**, and getting it wrong is silent: a publish after the commit stages its row in a fresh transaction that `get_db` closes without committing, and the event disappears with no error raised anywhere — demonstrated against a real Postgres rather than described, and held in place for all three call sites by `test_auth_events.py`. The claim is `lock_rows(..., skip_locked=True)` from `src/locking`, the first genuine consumer of the batch pattern that module was built for: any number of relays run concurrently, each taking a disjoint batch, and one that dies releases its rows the moment its transaction rolls back, so there is no lease to expire and no reaper to write. **`src/distributed_lock` is deliberately not used** though its own docs guessed it would be — it would make the relay a singleton, the opposite of what `SKIP LOCKED` buys, to solve a problem the row locks already solve. Claim, dispatch and outcome are one transaction because a row lock lives until COMMIT and that is what makes "claimed" mean anything; the cost is that a slow subscriber holds it, so every dispatch is bounded by a timeout. The relay calls `raise_for_failures()`, since the bus *reports* subscriber failures rather than raising them and a relay that ignored the report could not tell a delivered event from a dropped one — which is why the dispatcher protocol promises a `PublishResult` where `EventPublisher` promises `object`, and why a partially-failed fan-out re-delivers to subscribers that already succeeded (`event_id` is the dedupe key). Payloads are JSON scalars only, checked by exact type and refused in the request that introduced the field: a tuple would come back a list and a `StrEnum` a plain string, so the event a subscriber received would not equal the one published, in a frozen dataclass nobody thinks to doubt; non-finite floats are refused because jsonb rejects them at COMMIT, failing a request whose body mentions no floats. Failures are per event rather than per batch — abandoning the batch puts every event behind one poison row, which is how an outbox becomes an outage — and the backoff (`backoff_delay`, third caller, one policy) is computed from the row's `attempts` so it survives a redeploy. The database's clock writes and compares `available_at`, since a relay host with five minutes of drift would otherwise claim rows early or park them. Delivered rows are deleted: this is a queue, not a log, and a table keeping everything it ever relayed needs a retention job nobody has written. `run()` catches everything a tick can raise, because an exception escaping it would be stored on a task nobody awaits and the application would go on publishing into a table nothing drains. An event with no subscribers is a *successful* delivery, which makes the shutdown order load-bearing: `main.py` stops the relay before clearing the bus. There is no flag for writing rows — one would reintroduce the lost-event window in whichever deployment least expected it — only `OUTBOX_RELAY_ENABLED` for whether this process drains. No dead-letter queue and no attempt ceiling (Phase 8 owns that): a poison event retries forever at the capped interval, visible in `attempts` and `last_error` and unable to starve the queue, because a payload nobody can read is still a fact that happened. No ordering guarantee, and no dispatcher but the in-process bus. Driven end to end through a real uvicorn process as well as CI: a registration staged a row inside its transaction, the relay delivered it to the audit subscriber and the Celery welcome-email task, and the table was empty afterwards (PR #38)
- [x] `asyncio` structured concurrency: TaskGroup, cancellation, and timeout patterns — `src/structured`, documented in `docs/structured-concurrency.md`, 100% line coverage on all five new modules. Three holes `asyncio` leaves open, one module each, and all three are silent when they open. **A task has an owner** (`scope.py`): `asyncio.create_task` hands back a task the loop holds only *weakly*, so it can be collected mid-await, its exception is retrieved by nobody — it surfaces from a `__del__` at collection time, if at all — and it outlives the request whose `ContextVar`s it borrowed. `TaskScope` makes the lifetime lexical. `asyncio.TaskGroup` is used underneath rather than reimplemented, because the parts that look simple are the parts that are not: cancelling siblings on a child failure, collecting them into a `BaseExceptionGroup`, and the `uncancel()` bookkeeping that keeps an enclosing `asyncio.timeout` able to tell its own expiry from someone else's cancellation. **What TaskGroup does not have is an exit rule for a daemon:** `__aexit__` *waits*, so a `while True:` relay loop inside one hangs shutdown until SIGKILL truncates its batch — asserted against `asyncio` itself rather than described — and `WhenScopeExits.CANCEL` cancels first, then lets the group drain, the draining being load-bearing since `cancel()` only *schedules* the error and the coroutine has to be resumed for its `finally` to roll back. Factories rather than coroutines, matching `src/parallel/io.py`: a child the scope never starts would otherwise warn from the garbage collector somewhere unrelated in the log. Names on every child, because in a hung process `asyncio.all_tasks()` is the only evidence there is. The body's own exception is unwrapped from the group `TaskGroup` puts it in — keyed on object identity, so a child's failure never is, while children's failures stay grouped even when there is one, since otherwise the *type* of the exception would depend on how many happened to fail and the handler that worked in testing breaks the day two do. **A wait has a ceiling that composes** (`deadline.py`): three calls each given five seconds under a five-second budget take fifteen, so `deadline()` nests and clamps rather than extends. A clamped inner scope arms **no timer of its own** — two timers at one instant would both fire and cancel the same task, and the race would pick the error message, for a distinction that matters since "the request budget ran out" and "the payment gateway was slow" have different fixes; the enclosing scope owns the instant and names itself. `DeadlineExceeded` is deliberately **not** a `TimeoutError`: that inheritance would let a handler catching `TimeoutError` to retry an upstream catch the spent budget instead and retry inside a scope with no time left, and keeping them distinct is why `src/decorators/retry.py` needs no special case. A `TimeoutError` raised *by the body* is passed through untouched, so a slow socket is never reported as a spent budget. `expires_at` is `loop.time()` and never `time.monotonic()`, because under uvloop the epochs are unrelated and the monotonic form yields a deadline far in the past — it fails on uvloop and passes on the default loop, the worst way for it to fail. `clamp_to_deadline` raises rather than returning zero on a spent budget, since most clients read a non-positive timeout as "no timeout" and would wait forever at precisely the wrong moment. **Cleanup finishes** (`cancel.py`): a cancelled handler's `finally:` runs on a cancelled task, so the release that has to happen is exactly the `await` that gets cut, and it takes *two* cancellations to show — the first is caught, and a shutdown draining tasks or a `TaskGroup` aborting cuts the cleanup the first one started — which is why it never happens in development and happens under load. `asyncio.shield` is not the fix and is demonstrated not to be: it protects the work and not the *wait*, so the caller unwinds immediately and the cleanup keeps running unowned, turning "cleanup that got cancelled" into "cleanup that may or may not happen". `protect` keeps waiting and re-raises the cancellation afterwards; `finalize` re-arms it on the current task instead, so an `except:` block's own `raise` still propagates the original exception rather than an artefact of the cleanup, and the task still ends cancelled — deferred by the length of the cleanup, not discarded. Adopted where it fixes a real bug: `IdempotencyMiddleware` released its reservation with a bare `await` inside `except BaseException:`, the one await in that middleware guaranteed to run on an already-cancelled task, so a second cancellation left the reservation held and answering every retry with 409 for its full TTL — precisely the outcome that release exists to prevent. `test_the_reservation_is_released_despite_a_second_cancellation` fails against the old code and passes against the new, verified by reverting the one call rather than assumed. `tests/test_cancellation_gate.py` is the fitness function, in the style of the immutability gate: no discarded `create_task`/`ensure_future` (`TaskGroup.create_task` and `TaskScope.start_soon` are not matched — those *are* the owner), and no caught cancellation without a `raise`, `except BaseException:` and bare `except:` included while `except Exception:` is not, since `CancelledError` has been a `BaseException` since 3.8 precisely so it cannot be caught that way. Exemption tables are keyed by qualname, require a written reason, and reject a stale entry too, so an exemption cannot outlive the code it was written for; three cancellation exemptions (`OutboxRelay.stop`, `DistributedLock._stop_renewer`, `structured.cancel._drain`) and an empty task-ownership table. Three suites open with a `TestTheProblemBeingSolved` class asserting on `asyncio` itself, so the justification for the module fails the build if it ever stops being true, and cancellation is driven the way it arrives — an outer task cancelled from the test's task — rather than by raising `CancelledError` by hand, which would exercise the `except` clauses without the `uncancel`/`cancelling` bookkeeping where the interesting behaviour is. No conversion of the relay and lock renewer, which still hand-roll create-cancel-await-swallow and are exactly what `TaskScope` is for: converting them means restructuring `src/main.py`'s lifespan, whose teardown order is load-bearing and documented in place — the relay must stop before the bus is cleared, or its last batch is delivered to nothing and deleted. No per-request budget middleware, since what the budget should be is a deployment question and a wrong default fails requests that used to work, and no nursery-style `start()` that waits for readiness, which would mean guessing what "ready" means for every kind of child (PR #39)

## Phase 8 — Streaming & Messaging
- [x] `StreamingResponse` for large exports with backpressure-aware async generators — `src/streaming` plus `GET /api/v1/exports/users` (admin only), documented in `docs/streaming.md`, 100% line coverage on every new module. Three problems, and the third is the one usually skipped. **Producing and sending are the same coroutine**: hand `StreamingResponse` a plain async generator and every database read waits for the previous socket write, so a client on a slow link keeps a server-side cursor idle for the whole download — and the obvious fix, a task and a queue, is worse, because the obvious queue is unbounded and a producer faster than its client reads the entire table into it, which is the export materialised in memory with nothing raised until the OOM kill. `with_readahead` is one owned producer task behind a queue with a maximum size, so peak memory is `EXPORT_READAHEAD_CHUNKS × EXPORT_CHUNK_BYTES` and cannot become anything else; `TestTheProblemBeingSolved` asserts both halves against `asyncio.Queue` itself. The producer is a `TaskScope` child with `WhenScopeExits.CANCEL` rather than a bare `create_task`, which here would be every problem `src/structured` documents at once. **Once the first byte is sent the status line is spent** — the handlers are inside the middleware stack and Starlette re-raises rather than renders after a response has started — so a failure at row 400,000 either cuts the connection, leaving a truncated file that arrived with a 200, or the body admits to it. Nothing in HTTP rescues that: `Content-Length` is unknowable before the last row, chunked framing terminates cleanly either way, and NDJSON truncated at any line is *valid* NDJSON, so the consumer doing the obvious thing gets a short file and no error. Every stream therefore ends with a terminal record — `{"_export":"complete","records":N}` or a `failed` one carrying an application error code from `src/exceptions.py`, the same vocabulary the JSON envelope uses before the first byte — and its absence is how a client detects truncation; buffered records are flushed ahead of a failure so the count describes the body exactly, and an unexpected exception reports `INTERNAL_ERROR` with a fixed message rather than quoting a traceback into a body that is already public. Failures *before* the first byte stay ordinary 401/403/422 envelopes, which is why the generator is lazy rather than primed. **Nothing closes an abandoned generator**: Starlette iterates the body with `async for` and never calls `aclose()`, so a client disconnect leaves the generator — and the scope, task and cursor inside it — for the garbage collector, which is not a schedule a connection pool can be sized against; each layer now closes the one below it, and the middle one was found by a test rather than by reading, because breaking out of an `async for` closes nothing. The deadline is armed around the producer *task* and never inside the source generator, since `asyncio.timeout` cancels the task it was entered in and the cancellation lands wherever that task is suspended — usually `Queue.put`, a frame the generator's own `async with` would never see — which also makes it cover time spent blocked on a client that has stopped reading, that being a hold on the cursor exactly as effective as a slow query. The query names the eight published columns rather than `select(User)`, so the password hash is never fetched at all; **that is not a memory argument, and two earlier drafts of this claim were wrong until measured** — SQLAlchemy's identity map is weak-referencing, so streamed entities are collected as they go, and asyncpg tolerates an abandoned cursor rather than failing the next statement — so `tests/test_streaming_db.py` captures the emitted SQL to assert the hash is absent, asserts the entity query it replaces *does* contain it, and checks `AsyncResult.closed` instead of a query that would pass either way. Two encoding details are not stylistic: `allow_nan=False`, because Python's `NaN`/`Infinity` are not JSON and would break a consumer's parser in the middle of a large file, and U+2028/U+2029 escaped despite `ensure_ascii=False`, because `str.splitlines()` breaks on them and a display name containing one would split a record in half. No CSV — a truncated CSV is a valid CSV with nowhere to put a terminal marker a spreadsheet would not render as one more row of data — no background export job with a download link (`EXPORT_DEADLINE_SECONDS` is where the boundary to that is written down), no resumption, and nothing yet bounds how many exports run at once, each holding a pooled connection for its duration (PR #40)
- [x] Server-Sent Events endpoint with heartbeat and client disconnect detection — `src/sse` plus `GET /api/v1/events/stream`, documented in `docs/server-sent-events.md`, 100% line coverage on all seven new modules and the route. The keepalive is the *detector*, not decoration: Starlette reads the ASGI receive channel only below spec_version 2.4, so on the servers this runs on a vanished client is discovered by a `send()` that raises — nothing polls — and a stream with nothing to say makes no writes. An idle stream whose client has gone is therefore undetectable, its generator suspended holding a hub subscription until something is published on that topic, which for a per-user topic may be never and is also what repairs it. A comment frame every `SSE_HEARTBEAT_SECONDS` makes that interval the ceiling on how long an abandoned stream holds its resources; `tests/test_sse_endpoint.py` asserts it over a real socket against a real uvicorn, because httpx's `ASGITransport` buffers the whole body and never returns for a stream that does not end. Three more things stop being true once a response never ends. The status line is spent after the first frame, so a client that falls behind is closed with an `overflow` event rather than having events dropped under it — `EventStreamHub.publish` is a plain `def` with no awaits, so one slow browser can neither stall nor fail the request that produced the event. Every connection is a lifetime, ended by *finishing* the body rather than by raising, checked between frames because `asyncio.timeout` fires wherever the consuming task happens to be. And the wire format has no escaping, so a line break inside a value is a frame boundary: CR, LF and CRLF are normalised and nothing else is (`str.splitlines()` breaks on characters SSE passes through), while empty `data` and a NUL in `id` are refused because a client answers both by silently doing nothing. - [x] WebSocket endpoint with JWT auth, rooms, and per-connection rate limiting — `src/ws` plus `/api/v1/ws`, documented in `docs/websockets.md`, 100% line coverage on all five new modules and the route. Four things HTTP was doing for us stop at the upgrade, and each is a module rather than a function. **Authentication has nowhere to live**: a browser's `WebSocket` constructor cannot set a header, so `Authorization: Bearer` is unavailable to exactly the clients this is for, and the three ways around that are a token in the query string (written down by the access log, every proxy, browser history and `Referer` — refused here, with a test, because "it works anyway if you also send it properly" is how a rejected mechanism comes back), a first message after `accept()` (which inverts the property that makes authentication useful: the peer holds a socket and a task before proving anything, so the cheapest denial of service becomes connecting and saying nothing), and `Sec-WebSocket-Protocol`, which is what this uses — `["bearer.auth.v1", token]` is a request *header*, the tag is echoed on accept and the token never is, and a JWT is a legal subprotocol token only because base64url plus `.` happens to be. Two facts about refusing before the handshake completes were measured rather than assumed and are why the answer is a bare 403 with the reason in a log line: a close code passed before `accept()` is **discarded** (uvicorn answers HTTP 403 whatever you pass), and the ASGI 2.4 denial-response extension — which would have carried this API's usual 401 envelope — is advertised, produces the right bytes for a raw `httpx` request, and still is not usable, because uvicorn logs `ASGI callable returned without completing handshake` and the reference Python client reports `InvalidMessage: did not receive a valid HTTP response` instead of the status. **A credential now outlives its use**: a request finishes long before its token expires and a connection does not, so verifying `exp` only at the handshake grants an access that never ends — a role changed or a session revoked an hour ago is still live on a socket opened before it — and the connection carries the expiry as a deadline with its own close code (4401) because the remedy is refresh-then-reconnect rather than reconnect. `verify_access_token` moved to `src/auth/utils.py` so the two transports cannot drift on what a valid access token is. **There is no request to rate limit**: the whole connection is one request, so the per-address middleware counts it once however many messages arrive, and the replacement is per connection and deliberately does not sleep (the frames are already buffered, so sleeping in the receive loop stops draining what the sender is still filling), does not queue the overflow (a rate limit with a buffer is a memory limit), and bounds messages *and* bytes, since either alone is trivially evaded; consecutive violations, not total, disconnect. **Every peer is now a publisher**: a broadcast runs inside another client's receive loop, so `RoomRegistry.broadcast` holds the same never-blocks-never-fails invariant as the SSE hub for a sharper reason, and one outbound queue with one writer task per connection is what keeps two coroutines from interleaving frames on a socket ASGI does not make re-entrant. Also refused at the decoder: `NaN`/`Infinity`, which `json.loads` accepts and `json.dumps` will not re-emit — an asymmetry that is otherwise one sender's payload costing a whole room their connections, because it fails at the broadcast rather than at the sender. Two pre-existing bugs surfaced and were fixed: `RequestIDMiddleware` claimed to handle `websocket` scopes and could not (it built a `Request`, whose constructor asserts the scope is HTTP), so the first connection to this endpoint was a 500 the client saw as a rejected upgrade; and an overflowed connection waited for its next inbound frame to notice, which for a read-only room participant is never. A third was caught by `tests/test_cancellation_gate.py`, which rejected the pre-close flush for swallowing `CancelledError`. Not done, and written down rather than left to be found: cross-process fan-out (the seam is `broadcast`, as with `EventStreamHub.publish`), replay after reconnect, room authorisation beyond authentication, presence, and a per-account connection limit (PR #42)
- [x] Kafka producer/consumer (aiokafka) with consumer groups and manual commits — `src/kafka`, documented in `docs/kafka.md`, 100% line coverage on every new module bar the protocol stubs. Everything here follows from one fact: an offset is a per-partition watermark, not an acknowledgement of a record, and both of its consequences are silent when you get them wrong. A committed offset is `record.offset + 1` — committing the record's own offset replays it after every restart and looks perfect in a test that never restarts a consumer, so `ConsumedMessage.next_offset` is where the `+ 1` is written once. And **the per-event failure isolation `OutboxRelay` uses would *drop* records here**: skipping record 4 and committing through 5 does not retry 4, it declares it done. So the grain is per *partition* — a partition stops at its first failing record, is seeked back to it, and the others carry on. The seek is what makes the retry soon rather than after a restart or a rebalance: the client's position has already moved past the record, which is a bug no fake can reveal, so `tests/test_kafka_end_to_end.py` drives it through a real broker. The batch still commits what succeeded, so work already done is never repeated, and the head-of-line blocking on the stalled partition is the honest cost of ordering — the dead-letter queue next door is the escape, and until then a poison record retries at the capped backoff, visible in `kafka.partition_stalled` and in the group's lag. `enable_auto_commit=False` is deliberately *not* a setting: auto-commit stores offsets for records the fetcher handed over, on a timer, whether or not they were handled — at-most-once delivery arrived at by leaving a default alone, and a setting would let one environment variable change the delivery guarantee with no code to review. `auto_offset_reset` is `earliest` for the mirror-image reason, the driver's `latest` meaning a new group ignores everything produced before it started while looking healthy at zero lag. The producer is `acks="all"` plus `enable_idempotence=True`, which are one decision rather than two, and idempotence is honest about its bounds: it deduplicates one producer session's own retries and says nothing about the application publishing twice. The policy in `runner.py` imports no `aiokafka`, which is what lets a fake source assert *which* offsets were committed and *when* a seek happened, while one contract suite runs both transports and an in-process broker models partitions, key placement, groups, assignment and positions-that-are-not-offsets — enough to test and run without a cluster, and refusing what a real broker refuses (committing a partition you no longer own) so the fake cannot let a bug through. A `kafka` service was added to CI, because a suite that silently skips its integration half is how a backend rots; the broker's own log for the merged run records real joins, a two-member group splitting partitions, `__consumer_offsets` writes and the explicit `LeaveGroup` that `ConsumerRunner.stop` produces. That teardown goes through `finalize` from `src/structured` rather than a bare `await` in the `finally`, because shutdown cancels the loop and that await is the one guaranteed to run on an already-cancelled task — a member that vanishes without leaving keeps its partitions, unowned, until its session times out. Nothing in the application consumes or publishes: what to consume is an application question and a demonstration topic in the lifespan would join a consumer group on every deployment, so `MessagePublisherDep` and `create_consumer_runner` are the seams and `docs/kafka.md` has the entry point. No transactions (the producer is idempotent, not transactional), no schema registry, and no per-partition concurrency inside one member — more members is what a consumer group already gives you (PR #43)
- [x] Dead-letter queue with an exponential-backoff retry ladder — `src/dlq`, documented in `docs/dead-letter-queue.md`, 100% line coverage on all six new modules. `orders.events` fails over to `.retry.1` (5s), `.retry.2` (25s), `.retry.3` (125s), then `.dlt`, and three decisions shape the whole package. **A delay is a topic, not a sleep**, and `await asyncio.sleep(30)` inside a consumer is wrong twice over in ways that both look fine in development: it stalls the partition, reintroducing the head-of-line blocking a dead-letter queue exists to end inside the thing meant to fix it, and a sleep past `max.poll.interval.ms` gets the member evicted, so the record is not delayed at all — the whole assignment, the in-flight records included, is handed to somebody else, repeatedly. **The tier delay is fixed and never jittered**, which is the one place in this repository where the call goes the opposite way to `backoff_delay` and is exactly what makes the tier consumer's stall-at-the-head correct *and complete*: a tier is read in offset order, so stalling at the first record that is not due is only safe if due time rises with offset, and jitter is precisely what breaks that — forty seconds drawn at offset 0 makes ten seconds drawn at offset 1 wait the full forty, thirty seconds after it was due. The spreading jitter would have bought is already there for free, because records enter a tier at the moment they fail. **Per-key ordering is given up for records that fail**: a record that detours through a five-second tier is handled after records produced behind it, which is free for independent records (an email, a webhook, an index update) and last-write-wins with the wrong last write for a key whose records are a sequence of edits — so `with_dead_letter` is opt-in per handler rather than something `ConsumerRunner` does, and the honest stall stays available. Everything in the router falls out of one rule, that **the record is never dropped**: the routing publish is what makes committing past a failed record safe, so `PublishError` propagates all the way to the runner and stalls the partition rather than being logged and swallowed, because the alternative during a broker outage is a topic quietly emptying itself into nowhere. Two failures skip the ladder — a `MessageNotDecodableError`, which fails identically in fifteen minutes, and a record whose own `x-dlq-*` headers cannot be read, since reading a corrupt attempt count as zero would send it round the ladder on every pass forever while every log line called it a first failure; the second finds its dead-letter topic by inverting the topic *name*, the headers being the broken part. `RetryAfter` is added to `src/kafka/base.py` as a third handler outcome alongside returning and raising — the partition is seeked back and stopped, but no failure is counted and the wait is the one the handler named — because a retry consumer holding a record due in fifteen minutes would otherwise log `kafka.partition_stalled` against a partition in perfect health and, the runner's own backoff being full-jittered and capped at sixty seconds, be polled several hundred times to be told no; `ConsumeResult` gains `deferred`/`defer_delay` and the loop waits the *shorter* of the two, since overshooting costs a record's latency and undershooting costs one cheap poll. Three bugs were found while testing rather than left to be found: the replay count was lost at exactly the failure it exists to describe (a replayed record carries the lap count and no envelope, so `read` reports it — correctly — as never having failed, which is why `read_replays` is separate); a record reaching its *first* failure on a tier topic was stamped with the tier's own name as its origin, so its second failure tried to build a ladder on `orders.events.retry.1`, was refused, and the `ValueError` escaped `route` and stalled the partition forever — a loop introduced by the code meant to end one, checked against the failure it names by removing the fix; and a record with neither a key nor a value could not be republished at all, `validate_record` refusing it, so it is given a key derived from its position and flagged, and `replay` refuses a flagged record rather than putting it on a partition it never came from. Not done, and written down: nothing in this application consumes anything, so nothing uses the ladder (`create_dead_letter_runners` is the seam); topic creation, which a cluster with auto-creation off needs before the first failure (`ladder_for(...).topics` names all five); per-key ordering across a detour, which would need a per-key hold and is a different design; metrics, which is why `RouteOutcome` is returned rather than only logged; and a dead-letter queue for `OutboxRelay`, which is a row in a table and shares none of this — `docs/outbox.md` pointed at this item and now says why (PR #44)
- [x] Redis Streams consumer group with stalled-message claiming — `src/redis_streams`, documented in `docs/redis-streams.md`, 100% line coverage on all five new modules and on every branch of the sixth bar its `Protocol` stubs. Everything here follows from one fact that does *not* transfer from `src/kafka`: a consumer group's pending entries list acknowledges **messages**, where a Kafka group commits an offset per partition. So failure isolation is per message and nothing queues behind a bad one, which is why there is no retry ladder here — a failed message is left unacknowledged and reclaimed in place. And **nothing redelivers it on its own**: a pending entry stays owned, by name, by the consumer that read it, so a process that dies leaves work owned by a name nobody is running, indefinitely, with the group's lag reading zero and every dashboard green. Redelivery has to be asked for, and asking is `XPENDING` plus `XCLAIM` — which is what "stalled-message claiming" means and why it is the item. Three decisions, each a bug taken the other way. **Claiming comes before reading, every cycle**: with new messages first a busy stream starves the stalled ones forever, because the read returns a full batch every time and the scan never gets a turn — claiming first bounds recovery at `min_idle` plus one cycle however busy the stream is, and `claim_batch` bounds the cost the other way so a backlog cannot stop new work. **`min_idle` is a bet about our own handlers rather than about Redis**: claiming a message whose owner is alive gets it processed twice, concurrently, so it sits well above `handler_timeout` (60s against 30s, asserted by a test, because closing that gap is a one-line edit whose damage appears only under load). **The scan is `XPENDING` and the claim is `XCLAIM`, not one `XAUTOCLAIM`**: the extra round trip buys the delivery count *before* the claim, which is what lets a message over `max_deliveries` go to `<stream>.dead` instead of to a handler that has already failed on it four times — published first and acknowledged second, since the other order empties the stream into nowhere during an incident. Four behaviours were measured against a real Redis 7 rather than taken from the manual, and each is silent when you get it wrong: `XGROUP DELCONSUMER` **discards the consumer's pending entries** (four unread messages, one command, and they are not pending, not claimable, and not returned by `XREADGROUP >` either — the return value reads like a receipt and is a body count), which is why `stop()` removes this consumer only when it owes nothing and why the raw command is driven in a test; a claim increments the delivery counter and `JUSTID` does not, making `JUSTID` a trap here because a poison message whose counter never rises never reaches its cap; an entry can be in the PEL and gone from the stream, since `XDEL` and `MAXLEN` trimming consult no group and `XCLAIM` drops the dangling row silently, so `claim` reports what it asked for and did not get; and `BLOCK 0` blocks *forever*, so `read` never passes it. A group is created at `$` and not `0` — the opposite of Kafka's `earliest`, set explicitly so a first deploy does not replay a month of a retained stream — with `MKSTREAM` on so deployment order is not a correctness question. The contract suite runs against both an in-process model with an injectable clock and a real server, so every claim about idleness, ownership and counters is measured on each run. Not done, and written down: nothing in this application publishes or consumes, so nothing uses it yet (`create_stream_runner` is the seam and the lifespan is deliberately untouched); replay from the dead-letter stream; lag as an exported metric; and ordering across a claim, which is what Kafka's per-key partitioning next door is for (PR #45)

## Phase 9 — Resilience & Observability
- [x] Circuit breaker + retry with jitter on outbound httpx calls — `src/resilience`, documented in `docs/resilience.md`, 100% line coverage on all five new modules, applied as an `httpx.AsyncBaseTransport` and wired into both payment adapters. Everything follows from one split: a *transient* failure wants another attempt and a *sustained* one wants the attempts to stop, because every retry against a dead dependency holds a connection from a pool that a request to a healthy dependency now cannot have — which is how one slow third party takes an application down, by consuming everything that waits on it rather than by being slow. A transport rather than a decorator because an adapter written later gets the policy by being handed a client and cannot forget it, and because every input to the retry decision lives on the `Request` and the `Response`, which at that layer are the arguments. **Retryability and breaker-failure are one predicate**, since a failure not worth retrying is not evidence of an outage either: 429 and 5xx count, 501 and 505 do not (they answer identically in ten minutes), and no other 4xx does — a wave of 404s is this application asking for the wrong thing, and opening a circuit on it would take our bug and make it an outage for every other caller of that dependency. `PoolTimeout` is the mirror image and is neither retried nor counted: it is *this process* out of connections, so counting it opens a circuit on a remote service because of a local shortage and retrying it queues another waiter on the pool that is already full — left deliberately visible for the bulkhead item next door. **"May this be repeated" is two questions, not one**: a `ConnectError`/`ConnectTimeout` proves no connection existed to carry the request, so even a `POST` may repeat, while a read timeout, a write error and *every response status* happened with bytes on the wire and repeat only for an idempotent method — or a `POST` carrying `Idempotency-Key`/`PayPal-Request-Id`, which is a claim this layer cannot verify and so is opt-in per header name. Collapsing the two gives up free retries on the commonest failure in a rolling deploy, or double-posts under exactly the failure most likely to have worked. Three bugs were found by tests rather than left to be found: replayability was being asked *after* the send, where `httpx.MockTransport` had already buffered the body, so a one-shot `AsyncIteratorByteStream` looked replayable and the retry would have sent zero bytes — successfully — with the far end storing the empty version; the discarded response was held unread across the whole backoff, so the next attempt contended with its own predecessor for a pool slot; and a cancelled half-open probe stranded the circuit with no slots left and nothing that would ever report, which is why an outcome and a bare release are separate operations. The breaker sits *inside* the retry loop, so failures are counted per attempt and a circuit that opens mid-retry — on this request's failures or anyone else's — ends the loop instead of sleeping and re-sending underneath it; `CircuitOpenError` subclasses `httpx.TransportError` because `StripeGateway._request`, `PayPalGateway._fetch_token` and the webhook notifier already answer "could not reach it" by catching that, and a new exception family would escape all three and surface as an unhandled 500 at precisely the moment the breaker is supposed to be helping. Failures are counted in a bounded window rather than consecutively (any interleaved success resets a consecutive count, so a dependency failing half its calls never trips it), half-open admits one probe (the state exists to spend a single request finding out; admitting everyone is a thundering herd at a service that just came back), and closing takes two successes and clears the window or the first failure after recovery re-opens it. A `Retry-After` wins over the full-jitter backoff with a jitter draw added *on top* — the header is a floor the server asked for, and waking at exactly it puts every rate-limited client on the wire in the same millisecond — while one beyond `max_retry_after` ends the retrying rather than holding a socket for an hour. Not done, and written down: breaker state is per process (five replicas hold five opinions and each spends its own probe; sharing it is a network call to decide whether to make a network call); nothing bounds concurrency per dependency, which is the next item; no metrics, though `CircuitBreakerRegistry.states()` is the snapshot and every transition is logged; and `src/notifications/webhook.py` keeps its own delivery-level ladder, because layering this underneath it would make three attempts each into nine requests to an endpoint that asked for one (PR #46)
- [x] Bulkhead semaphores per dependency with hard timeouts — `src/resilience/bulkhead.py` plus `BulkheadTransport`, documented in `docs/bulkheads.md`, 100% line coverage on the new module and on every module it touches. The breaker next door limits a dependency that has *failed*; nothing limited one that is merely **slow**, which raises nothing, logs nothing, trips no breaker and satisfies every health check pointed at it — a dependency answering in 4s instead of 40ms does not fail, it multiplies its share of this process by a hundred, and everything unrelated to it starves. **Composition is the item, and both halves of the order are load-bearing.** The compartment sits *inside* the retry loop, so a slot is taken per attempt and given back before the backoff: a slot held across a sleep is capacity spent doing nothing at the moment the dependency has none to spare, and the consequence — a retry that finds the compartment full is refused — is correct rather than unfortunate, since a saturated dependency is exactly where a retry is the traffic worth shedding. The breaker sits *outside* it because the free test goes first: `CircuitBreaker.acquire` admits or raises in the same tick while `Bulkhead.acquire` can wait, so reversed, every call to a dependency already known to be down would queue for a slot before being told the circuit is open. Three decisions, each a bug taken the other way. **A refusal is not a timeout**: `BulkheadFullError` is an `httpx.TransportError` for the reason `CircuitOpenError` is one — every caller here already answers "could not reach it" by catching that base class, and a new family would surface as an unhandled 500 at the moment the bulkhead exists to help — but deliberately *not* an `httpx.TimeoutException`, which would say the far end failed to answer and would make `request_was_sent` treat a request that provably never left as possibly-delivered, which is precisely what stops a `POST` being repeated; `is_local_shortage` now covers it alongside `PoolTimeout`, one shortage caught at two depths, neither retried and neither counted, because counting a local shortage opens a circuit on a remote service that may be in perfect health and merely popular. `BulkheadTimeoutError` goes the other way and *is* a `TimeoutException`, because that one really is the dependency failing to answer — and it exists because **httpx's own timeouts are per phase and every one of them restarts whenever a byte moves**, so `read=10.0` bounds the wait for the next read rather than the exchange and a far end dribbling a header line every nine seconds never trips it, while `timeout=None` is legal and leaves no phase timeout at all. **The slot outlives the send**: `handle_async_request` returns at the response headers and httpx reads the body afterwards, so releasing on return would stop counting a call at the point it stops being interesting to the transport and long before it stops occupying the process — a dependency that answers headers instantly and then drips ten megabytes would consume no capacity at all — and the pre-closed case is not a footnote, since every `httpx.MockTransport` response arrives already closed (`Response.__init__` reads a `ByteStream` eagerly) and getting that branch wrong would have leaked a slot on every mocked call in the suite. **The queue is owned rather than borrowed**: `asyncio.Semaphore` gives the count and neither of the other two things needed — its waiter list has no ceiling, so a dependency that stops answering collects tasks forever and a concurrency limit becomes a memory limit, the failure this module exists to prevent one layer up; and it binds to the first event loop that contends on it, which a process-wide registry outlives — so the queue is an explicit FIFO deque of futures with the slot handed straight to the waiter at the head (a woken waiter that finds the slot taken can requeue indefinitely while later arrivals walk past it) and the fast path checks that nobody is waiting, not only that a slot is free. Two races were found by tests rather than left to be found, both costing one unit of capacity permanently with nothing logged: a waiter cancelled *after* being handed a slot has to pass it on rather than drop it, and a waiter whose timer fires in the same tick as the hand-off takes the slot rather than being refused holding it — that second branch cannot be provoked under CPython's `_run_once` ordering and carries the reason rather than a bare pragma, because that ordering is a guarantee of one loop implementation and this application runs on uvloop. Renaming somebody else's `TimeoutError` as ours is refused at the same boundary: `timer.expired()` separates this scope expiring from an enclosing `deadline()` firing or a `TimeoutError` raised underneath, the line `deadline()` already draws for the same reason. The enclosing deadline is consulted before queueing with three answers — no scope leaves the acquire timeout standing, a spent budget refuses without queueing at all, and a budget shorter than the acquire timeout arms no timer of our own and lets the enclosing scope expire and name itself, which is the rule `deadline()` applies to its own nesting. Found while building it and written down rather than quietly fixed: **clients from `resilient_async_client` have an unbounded connection pool** — the factory passes `httpx.Limits()` when the caller names none, and a bare `Limits()` leaves `max_connections` as `None`, the familiar 100 being `httpx.Client`'s own default and replaced wholesale — so nothing in this codebase has ever bounded outbound concurrency and the compartment is now the only thing that does, left that way because a per-dependency bound that sheds immediately with a typed error naming the origin beats a process-wide one that sheds after a full pool timeout with an anonymous `PoolTimeout`. Not done, and written down: the hard timeout bounds the request through to the headers and not the body, since `asyncio.timeout` cannot be held across the return and holding one across a `yield` in an async generator is unsafe (the *slot* is held to the close, so a dripping body still fills the compartment and still gets shed — it just does not get cut off); a `stream=True` response nobody closes leaks its slot, the same property httpx's own pool has; compartment state is per process, as breaker state is; this is not a rate limiter; metrics stop at `BulkheadRegistry.stats()` and the `bulkhead.rejected` log line; and nothing bounds concurrency to Postgres, Redis or Kafka this way, the compartments being per HTTP origin because that is where the transport seam is (PR #47)

- [x] Security headers middleware: CSP, HSTS, `X-Content-Type-Options`, referrer policy — `src/middleware/security_headers.py` plus `src/docs.py`, documented in `docs/security-headers.md`, 100% line coverage on both new modules. Three things made this more than four `response.headers[...]` lines. **The one response a middleware cannot reach is the error page**: Starlette installs the handler for bare `Exception` on `ServerErrorMiddleware`, which sits *outside* the user middleware stack, so the 500 envelope passes through nothing `add_middleware` can add — measured, not assumed, with a stamping middleware that marked a 200 and a 404 and not a 500. That is why the policy is a frozen value with a `headers_for()` method rather than logic inside `__call__`: `unhandled_exception_handler` stamps its own response from the same object, the split `render_app_exception` already makes in that file for the mirror-image reason. **HSTS is conditional and both failure modes are silent**: RFC 6797 §7.2 has browsers ignore it over plain HTTP, and sending it from `http://localhost:8000` would pin a developer's browser to HTTPS for localhost, across every project on that machine, for a year — so the condition is `scope["scheme"]`, which behind a TLS-terminating proxy comes from `X-Forwarded-Proto` via uvicorn's `--proxy-headers`, and a deployment that does not trust its ingress gets no HSTS and no warning. `preload` raises at construction without `includeSubDomains` and a year of `max-age`, because the header is well-formed without them and the only other feedback is a preload submission rejected weeks later by a person; `max-age=0` stays legal, being the only way back out. **The documentation pages were the real obstacle to `default-src 'none'`**: `/docs`, `/docs/oauth2-redirect` and `/redoc` each carry an inline `<script>`, so a strict `script-src` either breaks them or is written `'unsafe-inline'`, which is the same as having no policy — the third option, a per-response nonce, means owning the routes, since the value has to exist before the page is rendered. The app is built with `docs_url=None`/`redoc_url=None` and includes `build_docs_router()`, which calls FastAPI's own renderers unchanged and adds a `nonce` attribute to every inline script tag; `tests/test_docs_pages.py::test_every_inline_script_is_nonced` reads the nonce back out of each response's CSP header, so a FastAPI release that changes that markup fails the suite rather than the documentation UI. `style-src` keeps `'unsafe-inline'` and is the one loose directive *because* it carries no nonce: a nonce in a directive makes CSP Level 3 ignore `'unsafe-inline'` in that same directive, so noncing ReDoc's one `<style>` block would break every style its renderer adds afterwards. Every docs directive was read off the markup FastAPI actually emits, and lives in the module rather than in settings — what those pages load is a fact about them, not a deployment choice (PR #52)
- [x] Refresh-token reuse detection with family revocation — `refresh_tokens.family_id` plus `revoked_at`/`revoked_reason`, migration `0006`, documented in `docs/refresh-token-reuse.md`, 100% line coverage on `src/auth/service.py` and `src/repositories/refresh_token.py`. Rotation already made a refresh token single-use; what was missing was any response to a spent one coming back beyond refusing that request. **That refusal lands on the wrong party.** A stolen token is byte-identical to the original, so whoever refreshes *second* is the one who looks wrong — and an attacker polling every thirty seconds always refreshes first. Rotation alone therefore detects the breach and signs out the victim, leaving the thief a chain that renews itself indefinitely. RFC 9700 §4.14.2 resolves it by refusing to guess: `family_id` names the authorization grant — minted by a login, inherited unchanged by every rotation — and a replay revokes every live member of it. The owner loses a session and types a password; the attacker loses everything, having no password to type. **The commit before the raise is the whole mitigation, and omitting it is invisible**: `get_db` closes its session without committing, so a revocation still pending when `UnauthorizedError` propagates is rolled back on the way out — and the response is a 401 either way, which is to say every test that asserts a status code passes against a version that revokes nothing. `_handle_reuse` commits first and a test asserts the commit rather than the status; the suite is mutation-checked, and dropping that commit, revoking the single token instead of the family, or letting rotation mint a fresh family each fail it. **A detector that fires on every 401 is not a detector** but a way for anyone holding one stale token to end a live session, so expired, never-issued and wrong-type tokens are refused without revoking anything, and the replay 401 is byte-identical to the unknown-token 401 so the caller learns neither whether a guess was real nor whether a replay landed. Logout now revokes the family too, which fixed a case the old single-row revoke got wrong — a refresh racing a logout left a working successor behind — while presenting an already-revoked token to *logout* stays a retry rather than reuse. `family_id` is deliberately not a JWT claim: a grant id a client can read is one an attacker can correlate across stolen tokens, and the row is looked up by token string on every refresh anyway. `RefreshTokenReuseDetected` is not a `UserEvent` for the same kind of reason — that base requires an `email` the token row does not carry, and fetching one would add a query to the single path whose rate an attacker chooses (PR #53)
- [x] Field-level encryption at rest (AES-256-GCM) via a SQLAlchemy TypeDecorator — `src/encryption/` (six modules), migration `0007`, `scripts/generate_encryption_key.py`, documented in `docs/field-encryption.md`, 100% line coverage on every new module. Postgres already encrypts at rest and what that buys is precisely one thing: somebody cannot walk off with the disk. A leaked read replica, a `pg_dump` in a CI artifact, a restored snapshot in a staging account and a support session with `SELECT` all see plaintext, so the boundary moves to a key the database has never held. The cost is paid in queries, which makes this a per-column decision rather than a switch: **`users.notification_webhook_url` and nothing else**, because a user-supplied webhook URL is a credential in practice — Slack, Discord and most incident tools put the shared secret straight in the path — and because it is the one column in that table which is read and never searched. `email` and `oauth_sub` are looked up by equality and stay as they are; `hashed_password` is already one-way; `role` and `notification_channel` are low-cardinality enough that ciphertext would leak the value through its frequency anyway. A `TypeDecorator` rather than the service layer, because encryption placed in a service has to be remembered at every write and a column type cannot be forgotten — everything above the mapper still handles `str`. **The context label is in the AAD, and it binds the column rather than the row.** Without it every encrypted column sharing a key is interchangeable, and an attacker with `UPDATE` who cannot *read* a value can still *move* one; with it, a ciphertext written into a different column fails to authenticate. It does not bind the row, because a `TypeDecorator` sees one value and has no access to the primary key, so copying a sealed URL onto another user still decrypts — asserted in `test_moving_a_value_between_rows_is_not_caught` rather than left as a belief, since closing it needs a mapper-level event and makes inserting a row and its sealed values in one statement impossible. The label is a literal and not `f"{table}.{column}"`: deriving it would make a column rename silently re-key every row in it, with the first symptom arriving whenever somebody next read an old one, so a gate asserts each label matches where it lives today behind an exemption table, the `test_immutability_gate.py` idiom. **Randomised encryption makes `WHERE col = :value` match nothing, quietly** — the query runs, returns zero rows and looks like an absent record — so the comparator raises on `==`, `!=`, the four ordering operators, `in_`, `not_in`, `like` and `ilike`, while `IS NULL` stays legal because absence is not encrypted and cannot be without losing the ability to select on it. Keys are a ring with ids travelling in the clear inside every value, because rotation needs two live at once; the three-step order is written down and so is the one irreversible mistake, retiring a key before its rows are re-encrypted, which `UnknownKeyError` names so that putting it back is an available answer. `DataKey.__repr__` is hand-written and no error message in the package quotes material — a key logged once in a traceback lives wherever the logs aggregate. One trap was found by measurement rather than reasoning: `cipher_provider` is positional-or-keyword because SQLAlchemy builds a type's cache key from `get_cls_kwargs`, which ignores keyword-only parameters, so behind a `*` two types differing only by cipher are indistinguishable to the statement cache and one can execute with the other's compiled bind processor. The development and CI keys are published here on purpose — their base64 decodes to ASCII saying what they are — so `cp .env.example .env` boots, and `build_key_ring` refuses them anywhere in the ring, not merely as the active key, when `ENVIRONMENT=production`. Migration `0007` adds a `bytea`, encrypts every non-null value, drops the `varchar` and renames, the conversion being inexpressible in SQL; `downgrade()` needs every key any surviving row was sealed under and fails before dropping anything rather than leaving NULLs where URLs were. Not done, and written down: no blind index, so an encrypted column here is unsearchable full stop; no re-encryption job for rotation step 3; and no KMS indirection — `ENCRYPTION_KEYS` comes from the environment like `SECRET_KEY` does, so anyone who can read the process can read the keys (PR #54)
- [x] PII redaction processor in the structlog pipeline — `src/redaction/` (five modules), wired into `configure_logging`, documented in `docs/pii-redaction.md`, 100% line coverage on every new module. A log line is written once and kept for years, which is what turns a field that was fine to write into a subject-access request; reviewing every `logger.info` forever is not a control, and a processor the events cannot go round is. The leaks were already here: `request_id` middleware binds `query=` raw on every request, `celery_email` logs `to=`, and fifteen sites log `error=`, which is how an upstream 401 quoting the header it refused reaches a log. **Position is the decision, not the presence.** `configure_logging` builds one chain with *two* sinks on it, and the second is `log_forwarder`, so a redactor placed behind it cleans stdout and exports the original — the one order of the three that passes every test anyone naturally writes, because the test reads stdout. It therefore sits immediately before `structlog_processors()` and after `merge_contextvars`, and `TestTheChain` asserts the *exported record* rather than only the index, since an index can be satisfied by a chain that never exports. Two passes, because either alone fails: by field name on contiguous **word runs** — equality misses every field that exists, since nobody logs `password`, they log `password_hash`, and substring matching eats `passengers`, `tokenizer` and every `idempotency_key` and storage `key` this codebase already writes, which is how a redactor gets switched off within the month. Multi-word phrases are what make it usable here: **`key` is not sensitive** while `api key`, `private key` and `encryption key` are, and `name`, `address`, `id` and `signature` are deliberately off the list, each for a field it would have hollowed out (`event_name`, `ip_address`, the join key of every line, and the value you need in front of you when a webhook is being rejected). And by value shape, for the strings under names that say nothing — `error` must never become a sensitive key, so the string under it is examined instead. **Every detector validates before it redacts** (Luhn, ISO 13616 mod-97, a base64url-decoded JOSE header that has to name an `alg`, since `eyJ` alone is just the base64url of `{"` and every encoded JSON object starts with it), which is what keeps a sixteen-digit order id, an epoch-millis timestamp and a pagination cursor out of the marker; detectors with nothing to check — "looks like a phone number" — are left out, because their false positives land on the numbers an incident is being read for and they teach people that `[redacted]` means "ignore this". A field *named* `phone` is on the key list all the same: a name is a statement of intent where a shape is a guess. One pass is neither — `name=value` pairs are scanned with the *key* policy, because a query string is a sequence of named fields wearing the disguise of one value, and it is also what catches `otp=1234`, which has no shape at all. The walk is as conservative as the matching, so that a line with nothing sensitive in it comes out byte-identical to the line written today: numbers are untouched, since a card detector over integers would be redacting the `size`, `offset` and `status_code` fields this service is read through; foreign objects come back as *themselves* unless their rendering trips a detector, which costs nothing the renderer was not going to pay anyway and closes the `error=exc` hole; sets come back as lists, because redaction collapses distinct members onto one marker and a set would then swallow the duplicates, turning "three tokens were logged here" into "one was"; and cycles are detected against *ancestors* rather than everything seen, so a list appearing twice under different keys renders both times instead of the second being falsely called circular. It fails **closed** — the fields are dropped and `redaction_failed` is set — because a redactor that emits the original on error stops working on precisely the input strange enough to be worth hiding, while the line looks completely ordinary. `LOG_REDACTION_EXTRA_KEYS` can only widen: there is no setting that removes a name and none that turns redaction off, since that switch is one hurried incident away from being set by somebody who will not be the person who finds out a month later that it was never set back. One visible behaviour change, accepted rather than designed around: `distributed_lock` logs `token=lease.token` at debug and that is now redacted — a lease token is a capability, whoever reads one out of a log can release somebody else's lock, and `lock=` is what an incident actually reads. Not done, and written down: exception messages and tracebacks, which the forwarder hands to the OTLP SDK downstream of every processor and which do not reach stdout at all (the JSON renderer emits `"exc_info": true` and no traceback) — the rule that follows is not to interpolate user data into an exception message; numbers under a name the policy does not know; and free text, where a passport number in a `note` field passes straight through because nothing about it is checkable. Redaction is the last line, not a licence to log PII (PR #55)
