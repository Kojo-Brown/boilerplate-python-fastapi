## Phase 6 — SOLID & Design Patterns
- [x] SOLID audit with before/after refactors documented in `docs/solid.md` — audit in `docs/solid.md`; the LSP/ISP finding it turned up (bare `ValueError` as the universal auth failure signal) fixed by routing auth failures through domain exceptions (PR #25)
- [x] Factory pattern: `StorageFactory` returning S3/local/memory backends via `Protocol` — `StorageBackend` protocol in `src/storage/base.py` with no boto3, filesystem or settings import; `S3Storage`/`LocalStorage`/`MemoryStorage` implement it structurally and one parametrised contract suite runs against all three. Presigned URLs are deliberately left off the protocol — only S3 can mint them, so putting them there would trade an OCP violation for an LSP one — and stay on `S3Storage`, which is why `/api/v1/uploads` is unchanged. Closes finding 5 of `docs/solid.md` (PR #26)
- [x] Strategy pattern: pluggable `NotificationStrategy` chosen per user preference — `NotificationStrategy` protocol in `src/notifications/base.py` over `Notification`/`Recipient`/`NotificationResult`, free of SQLAlchemy, httpx and settings; `email`, `webhook` and `none` implement it structurally and one parametrised contract suite runs against all three. `Recipient` is deliberately not the `User` row — `recipient_from_user` is the only code aware of both, so a webhook body can never be assembled from an object carrying the password hash. The channel comes from `users.notification_channel` (migration 0003): a plain string rather than an enum, so adding a channel stays a `register` call instead of a migration plus a deploy-order problem; unknown values raise rather than silently defaulting, empty ones fall back. Webhook deliveries are HMAC-signed over `{timestamp}.{body}` so a capture cannot be replayed by rewriting the header, and user-supplied URLs are SSRF-checked — the one gap, a hostname that resolves privately, is documented and asserted by a test rather than implied away (PR #27)
- [x] Decorator pattern: `@cached`, `@retry`, `@timed` decorators preserving signatures via `ParamSpec` — in `src/decorators`, documented in `docs/decorators.md`, 100% line coverage. Signatures survive both halves of the round trip: a `ParamSpec` on every `__call__` for mypy, `functools.update_wrapper` for `inspect.signature`, which is how FastAPI builds a route's parameters. Each is a factory that must be called (`@timed()`, not `@timed`) — the bare form needs an implementation signature loose enough to take a function or nothing, which erases the `ParamSpec` link. `@retry` re-raises the original exception rather than a `RetryError`, because this API derives status codes from exception types and a wrapper would turn a 409 into a 500 on the third attempt; it also refuses to retry `CancelledError` even under `on=BaseException`, and checks exhaustion before `should_retry` so caller code is never run for a decision that no longer exists. `@cached` collapses concurrent misses behind a refcounted per-key lock and never caches a failure; it is per-process, and the docs say so before they say anything else. Two bugs the composition tests found were fixed rather than documented around: `@retry` over `@cached` took the sync branch and silently retried nothing (an `AsyncCachedFunction` is a callable object, not a coroutine function), and decorating a `functools.partial` raised `AttributeError` for a missing `__qualname__` (PR #28)
- [x] Observer pattern: async domain event bus with typed subscribers — `src/events`, documented in `docs/events.md`, 100% line coverage. `subscribe(event_type, handler)` is checked by mypy in both directions, and dispatch walks the MRO, so an audit log subscribing to `UserEvent` is an ordinary subscriber rather than a special case in `publish`. `publish` awaits its subscribers: `create_task` would drop exceptions nothing holds and outlive the request scope whose context it borrowed, so work that should not be paid for inline is enqueued to Celery from *inside* a subscriber. Subscribers run concurrently and fail independently — a broken mail queue cannot fail a registration that already committed — while cancellation propagates rather than being recorded as eight spurious failures, and a handler that merely overran its `timeout` is a failure. Every publish in `AuthService` sits after the commit so nothing reacts to a transaction that then rolls back, and nested publishes are counted in a `ContextVar` because a cycle here is a request that never returns. Subscribers are registered from the lifespan, not at import, so importing a module never starts sending mail. Two bugs the tests found were fixed rather than documented around: a `Subscription` compared field-wise, letting one from a *different* bus unsubscribe a local handler (identity handles now), and structlog reserves the `event` kwarg, so every publish raised `TypeError` until the log keys became `event_name`. The bus is in-process and forgets; the transactional outbox in Phase 7 is the durable answer (PR #29)
- [x] Adapter pattern: `PaymentGateway` protocol with two concrete adapters — `PaymentGateway` protocol in `src/payments/base.py`, free of httpx, any provider SDK and settings; `StripeGateway` and `PayPalGateway` translate it to two APIs that agree on almost nothing (form encoding vs JSON, integer minor units vs decimal strings, a static key vs a cached OAuth2 token, `Idempotency-Key` vs `PayPal-Request-Id`, a 402 `card_error` vs a 422 `INSTRUMENT_DECLINED`), and one parametrised contract suite runs against both. This is the adapter pattern rather than another strategy: the two are not one idea implemented twice but existing APIs this codebase does not control, so translation *is* the work. `Money` is integer minor units plus a currency-exponent table and refuses an unlisted currency rather than defaulting to two decimals — the default is wrong in both directions at once, turning the same ¥1000 into ¥10 at Stripe and ¥100,000 at PayPal. A decline is a 402 distinct from the 503 that means retry is safe, and the reverse mistake is tested too, since reporting our own malformed request as a declined card sends shoppers to their bank over our bug. PayPal's `charge` returns the *capture* id, not the order id the response leads with, because only a capture can be refunded — an order id would work all the way through checkout and fail at the first refund — and capture status wins over order status, an order reading COMPLETED while its capture is still PENDING being the difference between money that exists and money that does not. `ChargeRequest.reference` is required rather than optional because an optional idempotency key is one nobody passes. No retry or circuit breaker (Phase 9 owns that; the idempotency keys are what make adding it safe), no vaulting/subscriptions/webhook verification on the protocol (Stripe HMACs the raw body, PayPal fetches a certificate chain — adapter-specific, as presigned URLs are on `S3Storage`), and no route, which is the next item (PR #30)
- [x] Dependency inversion via FastAPI `Depends` + protocol-typed providers, overridable in tests — `AuthService` now takes four protocols (`UserStore`, `RefreshTokenStore`, `UnitOfWork`, `EventPublisher`) instead of building `UserRepository(db)` and holding a whole `AsyncSession` for two methods, which closes findings 4 (DIP) and 6 (ISP) of `docs/solid.md` — the same seam, cut once. `src/dependencies.py` is the composition root: every provider is annotated with the protocol and returns the implementation, so mypy fails the build the day one drifts, and the concrete names appear nowhere else in the request path — `src/auth/router.py` no longer imports `get_db` at all. `Depends` alone injects without inverting; the protocols are what make the substitution possible. There is no unit-of-work adapter class because `AsyncSession` already satisfies `UnitOfWork` structurally, and no `rollback` on it because nothing calls one. `EventPublisher.publish` returns `object` rather than `PublishResult`, since every caller here discards it on purpose. The three DB-backed providers each take the session through `Depends(get_db)`, which FastAPI caches per request: load-bearing rather than an optimisation, since three sessions would have the unit of work committing a transaction the repositories never wrote to, and a registration answering 201 while persisting nothing. The protocols still name the SQLAlchemy models, a bounded compromise documented in place — the cost of a concrete model is that a fake must construct one, where the cost of a concrete repository was that a fake had to *be* a session. `tests/fakes.py` is the payoff: the auth, OAuth and event suites now run the real service over in-memory stores, seeded by what exists rather than by the order the service happens to query in — the stub they replaced answered `execute()` from a `side_effect` list, so adding a lookup shifted every later answer onto the wrong question in silence. A fitness function parses the imports of `src/auth/service.py` and `src/auth/router.py`, so the one-line regression that reintroduces finding 4 fails a test instead of passing review. No payments route: charging a card needs the `Idempotency-Key` middleware that opens Phase 7, and a charge endpoint that dedupes nothing turns a retried request into a second charge — `PaymentGatewayDep` is wired and waiting for it. Documented in `docs/dependency-injection.md` (PR #31)

## Phase 7 — Concurrency & Data Integrity
- [x] Idempotency middleware: `Idempotency-Key` + Redis dedupe with response replay — `IdempotencyStore` protocol in `src/idempotency/base.py` with Redis and in-memory backends behind one contract suite, and the ASGI middleware in `src/middleware/idempotency.py`; documented in `docs/idempotency.md`, 100% line coverage on every new module bar the protocol stubs. Middleware rather than a dependency because a dependency runs inside the route — it can see the request but not the response, and the response is what has to be replayed — and cannot cover the endpoint someone forgets to decorate, which is the one that will double-charge. Redis's `SET NX EX` is the reservation: a `get`-then-`set` pair lets two simultaneous retries both find nothing and both execute, so the contract suite measures that with 20 concurrent reservations against a real server rather than asserting it. Two TTLs, because one value cannot be both — a reservation expires in 60s so a worker killed mid-request cannot answer its own retries with 409 for a day, while a completed record lives 24h, which is a question about the client's retry window. Keys are namespaced by `sha256(Authorization)`: keys are client-chosen, so two callers will eventually pick the same one and the second would otherwise be handed the first's response. 5xx, 408, 425 and 429 release the reservation instead of being stored, since pinning a transient failure to a key answers the retry it invites with the very error being retried; an exception releases it too, `CancelledError` included. `Set-Cookie` is stripped from stored responses. Reuse is checked before in-progress so a client bug is a 422 rather than 409 or 422 depending on timing, and the store failing is a 503 by default because serving the request anyway is the double execution the caller asked to be protected from. Added *before* `RequestIDMiddleware` so it runs inside it: idempotency logs carry the replaying request's id and a replay is stamped with a fresh `X-Request-ID`, asserted from outside. `render_app_exception` was split out of `app_exception_handler` because exception handlers are installed inside the middleware stack, so a short-circuit never reaches them and would otherwise grow a second error envelope. No route requires a key yet — that is a per-route dependency, not middleware policy — and idempotency is not a transaction: a handler that commits and then dies before the response is stored still re-executes, which the transactional outbox later in this phase is the durable answer to (PR #32)
- [x] Optimistic concurrency: SQLAlchemy `version_id_col` + `If-Match`/ETag, 412 on conflict — `src/concurrency` holds the HTTP half (`EntityTag`, `IfMatch`, `resource_version_tag`, free of SQLAlchemy), `User.__mapper_args__["version_id_col"]` the storage half, and `/api/v1/users/me` is where they meet; documented in `docs/optimistic-concurrency.md`, 100% line coverage on every new module. The precondition is checked twice deliberately: `require_match` is the check that fires in practice and is the only one that can name the current tag, while the `WHERE version = :loaded` SQLAlchemy appends is the one that is *sound* — between the comparison and the write there is a window only the database can adjudicate, and keeping just the first leaves a lost-update race no test issuing one request at a time would ever reveal. `If-Match` uses strong comparison (RFC 9110 §13.1.1), so `W/"…"` never satisfies it; a comma is a legal `etagc`, so the header is scanned against the grammar rather than split on commas; an unparseable precondition is a 400 rather than a silent pass, because ignoring it switches the protection off exactly when the client believed it was on; a missing one is 428 rather than a blind overwrite. The tag carries the row id as well as the version — every row is at version 1 when created and `/users/me` is one URI naming a different row per bearer token, so a bare `"1"` from one client would compare equal to someone else's row — and those responses are `Cache-Control: private, no-store` for the same reason. 412 is kept distinct from 409: one means re-read and retry, the other means repeating the request fails identically. `tests/test_optimistic_concurrency_db.py` runs two real transactions at one row against the CI Postgres (skipped only when `DATABASE_URL` is unreachable, as the Redis leg of the idempotency contract suite is) and found a real bug while being written: logging `user.version` inside the `StaleDataError` handler reloaded an expired attribute through the session the failed flush had already killed, turning the 412 into a 500. No `If-None-Match`/304 — that is a caching question, not a correctness one — and no decorator wrapping the pattern, since *which* tag is current differs per resource and a wrong guess fails open (PR #33)
- [x] Pessimistic locking with `with_for_update()` and a deadlock-retry wrapper — `src/locking` holds the two halves that are only useful together: `rows` takes the locks (`lock_row`, `lock_rows`, `lock_timeout`, and a `LockMode` enum over all four Postgres row locks) and `retry` re-runs a transaction Postgres killed to break a deadlock. Documented in `docs/pessimistic-locking.md`, 100% line coverage on all four new modules. **The retry cannot be `@retry` from `src/decorators`, and not for stylistic reasons:** a Postgres transaction is dead after any error, so re-running a statement inside it does not reproduce the deadlock — it raises 25P02, and attempt three would raise it again. The retry is only sound with a `ROLLBACK` between attempts, which a general-purpose call retrier has no business knowing about; the backoff *policy* is not duplicated, since `backoff_delay` moved to `src/decorators/base.py` and both loops call it. **A lock over a stale in-memory copy protects nothing, and the ORM hands you one by default** — a `SELECT ... FOR UPDATE` for a row the session already holds takes the lock and returns the *cached* instance, because the identity map wins over the result set, so the caller decides against values read before the lock existed. That is the race the lock was for, failing silently in code that looks correct; both functions run `populate_existing=True` through one shared helper, and a test demonstrates the broken form rather than describing it. `Session.get(..., with_for_update=...)` is the obvious alternative and is refused: it routes through the refresh path, which turns on version checking, so a pessimistic reader of a row carrying the item-2 `version_id_col` gets `StaleDataError` instead of the current row it asked for. Classification is by SQLSTATE and never by exception class, since SQLAlchemy returns `DBAPIError` for a deadlock, a lock timeout and a unique violation alike under asyncpg; 55P03 is deliberately not retryable, because it is what `nowait` and `lock_timeout` raise and a retry loop is exactly the queue the caller refused. The CI Postgres 17 service log records the real `deadlock detected`, the `canceling statement due to lock timeout` and the `division by zero` → `current transaction is aborted` pair, so none of these tests silently skipped. No route consumes it: nothing in the schema has a balance, a stock count or a queue, and a lock on a route that does not need one is a worked example pretending to be a requirement — the transactional outbox later in this phase is the first genuine consumer, claiming rows with the `FOR UPDATE SKIP LOCKED` batch pattern. No advisory locks (`pg_advisory_xact_lock` is a different idea; the Redis item next door covers the cross-process case) and no `of=` on the lock clause (PR #34)
- [x] Distributed lock via Redis with fencing tokens, exposed as an async context manager — `src/distributed_lock`, documented in `docs/distributed-locking.md`, 100% line coverage on the context manager, the in-memory backend and the factory, 99% on the Redis one. **The token is the feature and the lock is the optimisation**, which is the opposite of how these are usually built: every acquisition is a lease, because a lock without one is held forever by any worker that dies inside it, and the price of that guarantee is that a lease can expire while its holder still believes it holds one — a GC pause, a blocked event loop, a partition, and the holder finds out late or never. Renewal narrows that window and cannot close it, since the pause can land between the last renewal and the write; no lock server closes it either, Redlock included, because a quorum still cannot bound a client's pause. So each acquisition mints a strictly increasing, never-reused token and the *resource* refuses anything lower (`WHERE fence < :token`, or `require_fence` where the resource is not a row), which is why `Lease.token` is part of the protocol rather than a detail of the Redis encoding. The fence counter therefore has no TTL and **must not be evictable** — if it goes, the next `INCR` returns 1 and the check silently stops rejecting the writers it exists to reject, so `maxmemory-policy` must not be an `allkeys-*` policy, and an async failover replays tokens for the same reason, stated in the docs rather than implied away. Every operation is one Lua script: a `get`-then-`set` acquire lets two workers into the same section, measured with 20 concurrent acquisitions against the real server rather than asserted. Release compares before deleting, since a bare `DEL` after your lease expired frees whoever came next and a third caller walks into the section they are still running — hence three release outcomes rather than a bool. The token is stable across renewals, because it identifies the lease and not the renewal, and bumping it would fence a holder out of its own earlier writes. A lease the store reports gone raises `LockLostError` on a clean exit — reporting success for work that may have been fenced out is worse than a 409 — but never over the body's own exception, and never for a release the store simply did not answer, which is no evidence the lease had ended. Not reentrant: a second lease for one owner would let an inner block's release free the outer block's lock. `wait_timeout` defaults to 0, mirroring `nowait` in `src/locking/rows.py` (a retry loop is a queue), and the wait reuses `backoff_delay` from `src/decorators/base.py` rather than adding a third backoff policy. No fail-open switch, unlike `IDEMPOTENCY_FAIL_OPEN`: running a section whose coordination is unreachable is the concurrent execution the lock was taken to prevent. No route consumes it — nothing here needs cross-process exclusion yet, and a lock on a route that does not need one is a worked example pretending to be a requirement — so `LockBackendDep` is wired and waiting for the transactional outbox later in this phase (PR #35)
- [x] GIL-bound work offloaded to `ProcessPoolExecutor`; IO-bound to `asyncio.gather` with semaphores — `src/parallel`, documented in `docs/parallel-execution.md`, 100% line coverage on all five new modules. Two problems that look alike and have opposite fixes: a handler *waiting* on IO leaves the loop thread idle, so overlap the waits; a handler *computing* holds it, so overlapping buys nothing — and neither does a thread, since the GIL means a compute-bound thread takes the interpreter away from the loop exactly as a coroutine does. `run_in_threadpool` is right for blocking calls that release the GIL (a sync driver, `open()`, argon2) and wrong for compute, which is why the CPU half exists at all. **`fork` is refused rather than discouraged:** a forked child of this process inherits the SQLAlchemy pool's open sockets, the Redis client's and the loop's epoll set, and two writers on one Postgres connection do not fail cleanly — they interleave protocol frames and return one request's rows to another; `fork` with threads is undefined at the POSIX level besides, and uvicorn runs threads, so `Settings` types the field `Literal["spawn", "forkserver"]` and fails at start-up rather than at the first offload. **The deadline is armed inside the worker with `setitimer`**, because `asyncio.wait_for` around an executor future cancels the wait and never the work — a runaway call would hold its slot forever while the parent politely reported a timeout, and a few of those leave the pool with no capacity and nothing in the log. `WorkerDeadline` derives from `BaseException` so an ordinary `except Exception:` in the workload cannot swallow it, measured against a workload that tries rather than asserted. There is deliberately no parent-side timer racing it: a wait measured from submission includes queue time, so under load it would fire first and report a timeout for a call that had not started — `timeout` is a budget for the call, and queue time is bounded separately by admission control. The two limits are stated rather than papered over (no `setitimer` on Windows; a C extension holding the GIL never reaches the bytecode boundary a handler needs), and `spin_with_alarm_blocked` reproduces the second deterministically so the fallback path runs in CI instead of for the first time in a deployment. **Admission control replaces an unbounded queue** — `ProcessPoolExecutor` queues without limit and queued submissions sit in the *parent's* memory as pickled payloads, so past `workers * (1 + depth)` calls get a 503 rather than growing the heap under a spike whose clients have already given up — and a `BrokenProcessPool`, which is terminal for an executor, is recovered by replacing it, since otherwise one OOM kill takes the endpoint down until the pod restarts. On the IO side, the two things wrong with plain `asyncio.gather` are asserted against `asyncio` itself in `TestTheProblemBeingSolved`, so the justification fails the build if it ever stops being true: it is unbounded, and with `return_exceptions=False` it propagates the first exception while leaving the siblings running, so a handler that fans out five calls and returns 502 leaves four in flight holding connections. `gather_bounded` caps concurrency and cancels the rest *and awaits them* — the awaiting is load-bearing, since `cancel()` only schedules a `CancelledError` and the coroutine must be resumed for its `finally` to run — takes factories rather than coroutines so awaitables are built one per slot, and returns input order. `run` keeps a pure `ParamSpec` and the deadline rides on `with_timeout(...)`, the same shape as `DeadlockRetryPolicy` and for the same reason: a `ParamSpec` cannot carry parameters after `*args`, so a `timeout=` keyword would have cost call-site argument checking. No route consumes either half — what to offload and how long to allow it are properties of the work, and a demo endpoint would be a worked example pretending to be a requirement — so `CpuPoolDep` is wired and waiting. The semaphore bounds concurrency and not rate; an upstream that publishes a rate needs a token bucket as well (PR #36)
- [x] Immutability: frozen Pydantic models, `Final`, and frozen dataclasses for value objects — `FrozenDict` in `src/immutable.py`, documented in `docs/immutability.md`, 100% line coverage. Each of Python's three tools guards exactly one edge, and this codebase was relying on them for a guarantee none of them gives. **`Final` is about the name, not the object:** twelve `Final` names held a writable dict and `__all__` held a writable list, so `CURRENCY_EXPONENTS["JPY"] = 2` type-checked, ran, and would have converted yen wrongly for the life of the process. The registry defaults were the sharpest of them, since each registry's `reset()` rebuilds from `dict(DEFAULT_*)` — one write to the constant poisons the escape hatch itself, permanently and for every test that runs afterwards. **`frozen=True` is about the attribute, and it does not copy:** `ChargeRequest(..., metadata=d)` stayed aliased to the caller's `d`, and both payment adapters send `metadata` upstream, so an edit between construction and the HTTP call reaches the provider's records while the request that was validated says something else; `Notification` has the same shape with delivery asynchronous, so "what the caller's dict says now" is not what it said when the notification was built. **Pydantic adds a third gap:** validation replaces the container, so a frozen model holds a dict it built. `FrozenDict` closes all three by copying on construction and exposing no mutator. It is not a `dict` subclass — that inherits six mutators each needing an override, and `dict.update` in C does not route through `__setitem__` anyway. It is hashable, which a frozen dataclass with a plain-dict field is not, so such a value object could not be a set member or an argument to a `@cached` function. It is picklable, which `MappingProxyType` is not, and `Notification` goes onto a Celery queue while `src/parallel` pickles arguments into worker processes. One Pydantic core schema wrapping Pydantic's own dict schema lets the same type serve module constants, dataclass fields and model fields with the OpenAPI document unchanged. `Settings` is frozen for a load-bearing reason rather than a tidy one: `get_strategy` is `@cache`d, the storage and payment registries build from a `Settings` at first use, and the idempotency and lock backends are built once in the lifespan, so a write to the singleton used to take effect for whatever had not been built yet and nothing else — the worst failure shape available, since every individual piece behaves exactly as designed. `CursorPage.items` is a tuple and `PresignedUploadResponse.fields` a `FrozenDict`, because a frozen model with a mutable container field is frozen in name only and the S3 POST policy signs those fields. `tests/test_immutability_gate.py` walks every module under `src/` and fails on a mutable `Final` constant, an unfrozen dataclass or an unfrozen model, with exemption tables that require a written reason and reject both a stale entry and an empty one — it found three constants a manual pass had missed. Two exemptions are recorded, the cache entry and the in-memory lock's held-lease record, both state rather than values. Deep immutability is deliberately not claimed: `FrozenDict[str, list[int]]` still hands out the same lists, and `hash()` is what complains (PR #37)
- [x] Transactional outbox: event row in the same session, async relay publisher — `src/outbox`, migration `0005`, documented in `docs/outbox.md`, 100% line coverage on every new module bar the protocol stubs. An event and the change that caused it are two systems with no transaction between them, and the codebase had already picked its poison: `AuthService` published *after* `uow.commit()` so nothing could react to a rolled-back transaction, at the price of losing the reaction outright if the process died in the gap. Moving the call does not close that gap, it swaps which half can happen alone — so publishing now writes a **row** in the caller's own session, and `OutboxPublisher` being an `EventPublisher` means every producer keeps its one-line call. **The ordering rule inverts as a result**, and getting it wrong is silent: a publish after the commit stages its row in a fresh transaction that `get_db` closes without committing, and the event disappears with no error raised anywhere — demonstrated against a real Postgres rather than described, and held in place for all three call sites by `test_auth_events.py`. The claim is `lock_rows(..., skip_locked=True)` from `src/locking`, the first genuine consumer of the batch pattern that module was built for: any number of relays run concurrently, each taking a disjoint batch, and one that dies releases its rows the moment its transaction rolls back, so there is no lease to expire and no reaper to write. **`src/distributed_lock` is deliberately not used** though its own docs guessed it would be — it would make the relay a singleton, the opposite of what `SKIP LOCKED` buys, to solve a problem the row locks already solve. Claim, dispatch and outcome are one transaction because a row lock lives until COMMIT and that is what makes "claimed" mean anything; the cost is that a slow subscriber holds it, so every dispatch is bounded by a timeout. The relay calls `raise_for_failures()`, since the bus *reports* subscriber failures rather than raising them and a relay that ignored the report could not tell a delivered event from a dropped one — which is why the dispatcher protocol promises a `PublishResult` where `EventPublisher` promises `object`, and why a partially-failed fan-out re-delivers to subscribers that already succeeded (`event_id` is the dedupe key). Payloads are JSON scalars only, checked by exact type and refused in the request that introduced the field: a tuple would come back a list and a `StrEnum` a plain string, so the event a subscriber received would not equal the one published, in a frozen dataclass nobody thinks to doubt; non-finite floats are refused because jsonb rejects them at COMMIT, failing a request whose body mentions no floats. Failures are per event rather than per batch — abandoning the batch puts every event behind one poison row, which is how an outbox becomes an outage — and the backoff (`backoff_delay`, third caller, one policy) is computed from the row's `attempts` so it survives a redeploy. The database's clock writes and compares `available_at`, since a relay host with five minutes of drift would otherwise claim rows early or park them. Delivered rows are deleted: this is a queue, not a log, and a table keeping everything it ever relayed needs a retention job nobody has written. `run()` catches everything a tick can raise, because an exception escaping it would be stored on a task nobody awaits and the application would go on publishing into a table nothing drains. An event with no subscribers is a *successful* delivery, which makes the shutdown order load-bearing: `main.py` stops the relay before clearing the bus. There is no flag for writing rows — one would reintroduce the lost-event window in whichever deployment least expected it — only `OUTBOX_RELAY_ENABLED` for whether this process drains. No dead-letter queue and no attempt ceiling (Phase 8 owns that): a poison event retries forever at the capped interval, visible in `attempts` and `last_error` and unable to starve the queue, because a payload nobody can read is still a fact that happened. No ordering guarantee, and no dispatcher but the in-process bus. Driven end to end through a real uvicorn process as well as CI: a registration staged a row inside its transaction, the relay delivered it to the audit subscriber and the Celery welcome-email task, and the table was empty afterwards (PR #38)
- [x] `asyncio` structured concurrency: TaskGroup, cancellation, and timeout patterns — `src/structured`, documented in `docs/structured-concurrency.md`, 100% line coverage on all five new modules. Three holes `asyncio` leaves open, one module each, and all three are silent when they open. **A task has an owner** (`scope.py`): `asyncio.create_task` hands back a task the loop holds only *weakly*, so it can be collected mid-await, its exception is retrieved by nobody — it surfaces from a `__del__` at collection time, if at all — and it outlives the request whose `ContextVar`s it borrowed. `TaskScope` makes the lifetime lexical. `asyncio.TaskGroup` is used underneath rather than reimplemented, because the parts that look simple are the parts that are not: cancelling siblings on a child failure, collecting them into a `BaseExceptionGroup`, and the `uncancel()` bookkeeping that keeps an enclosing `asyncio.timeout` able to tell its own expiry from someone else's cancellation. **What TaskGroup does not have is an exit rule for a daemon:** `__aexit__` *waits*, so a `while True:` relay loop inside one hangs shutdown until SIGKILL truncates its batch — asserted against `asyncio` itself rather than described — and `WhenScopeExits.CANCEL` cancels first, then lets the group drain, the draining being load-bearing since `cancel()` only *schedules* the error and the coroutine has to be resumed for its `finally` to roll back. Factories rather than coroutines, matching `src/parallel/io.py`: a child the scope never starts would otherwise warn from the garbage collector somewhere unrelated in the log. Names on every child, because in a hung process `asyncio.all_tasks()` is the only evidence there is. The body's own exception is unwrapped from the group `TaskGroup` puts it in — keyed on object identity, so a child's failure never is, while children's failures stay grouped even when there is one, since otherwise the *type* of the exception would depend on how many happened to fail and the handler that worked in testing breaks the day two do. **A wait has a ceiling that composes** (`deadline.py`): three calls each given five seconds under a five-second budget take fifteen, so `deadline()` nests and clamps rather than extends. A clamped inner scope arms **no timer of its own** — two timers at one instant would both fire and cancel the same task, and the race would pick the error message, for a distinction that matters since "the request budget ran out" and "the payment gateway was slow" have different fixes; the enclosing scope owns the instant and names itself. `DeadlineExceeded` is deliberately **not** a `TimeoutError`: that inheritance would let a handler catching `TimeoutError` to retry an upstream catch the spent budget instead and retry inside a scope with no time left, and keeping them distinct is why `src/decorators/retry.py` needs no special case. A `TimeoutError` raised *by the body* is passed through untouched, so a slow socket is never reported as a spent budget. `expires_at` is `loop.time()` and never `time.monotonic()`, because under uvloop the epochs are unrelated and the monotonic form yields a deadline far in the past — it fails on uvloop and passes on the default loop, the worst way for it to fail. `clamp_to_deadline` raises rather than returning zero on a spent budget, since most clients read a non-positive timeout as "no timeout" and would wait forever at precisely the wrong moment. **Cleanup finishes** (`cancel.py`): a cancelled handler's `finally:` runs on a cancelled task, so the release that has to happen is exactly the `await` that gets cut, and it takes *two* cancellations to show — the first is caught, and a shutdown draining tasks or a `TaskGroup` aborting cuts the cleanup the first one started — which is why it never happens in development and happens under load. `asyncio.shield` is not the fix and is demonstrated not to be: it protects the work and not the *wait*, so the caller unwinds immediately and the cleanup keeps running unowned, turning "cleanup that got cancelled" into "cleanup that may or may not happen". `protect` keeps waiting and re-raises the cancellation afterwards; `finalize` re-arms it on the current task instead, so an `except:` block's own `raise` still propagates the original exception rather than an artefact of the cleanup, and the task still ends cancelled — deferred by the length of the cleanup, not discarded. Adopted where it fixes a real bug: `IdempotencyMiddleware` released its reservation with a bare `await` inside `except BaseException:`, the one await in that middleware guaranteed to run on an already-cancelled task, so a second cancellation left the reservation held and answering every retry with 409 for its full TTL — precisely the outcome that release exists to prevent. `test_the_reservation_is_released_despite_a_second_cancellation` fails against the old code and passes against the new, verified by reverting the one call rather than assumed. `tests/test_cancellation_gate.py` is the fitness function, in the style of the immutability gate: no discarded `create_task`/`ensure_future` (`TaskGroup.create_task` and `TaskScope.start_soon` are not matched — those *are* the owner), and no caught cancellation without a `raise`, `except BaseException:` and bare `except:` included while `except Exception:` is not, since `CancelledError` has been a `BaseException` since 3.8 precisely so it cannot be caught that way. Exemption tables are keyed by qualname, require a written reason, and reject a stale entry too, so an exemption cannot outlive the code it was written for; three cancellation exemptions (`OutboxRelay.stop`, `DistributedLock._stop_renewer`, `structured.cancel._drain`) and an empty task-ownership table. Three suites open with a `TestTheProblemBeingSolved` class asserting on `asyncio` itself, so the justification for the module fails the build if it ever stops being true, and cancellation is driven the way it arrives — an outer task cancelled from the test's task — rather than by raising `CancelledError` by hand, which would exercise the `except` clauses without the `uncancel`/`cancelling` bookkeeping where the interesting behaviour is. No conversion of the relay and lock renewer, which still hand-roll create-cancel-await-swallow and are exactly what `TaskScope` is for: converting them means restructuring `src/main.py`'s lifespan, whose teardown order is load-bearing and documented in place — the relay must stop before the bus is cleared, or its last batch is delivered to nothing and deleted. No per-request budget middleware, since what the budget should be is a deployment question and a wrong default fails requests that used to work, and no nursery-style `start()` that waits for readiness, which would mean guessing what "ready" means for every kind of child (PR #39)

## Phase 8 — Streaming & Messaging
- [x] `StreamingResponse` for large exports with backpressure-aware async generators — `src/streaming` plus `GET /api/v1/exports/users` (admin only), documented in `docs/streaming.md`, 100% line coverage on every new module. Three problems, and the third is the one usually skipped. **Producing and sending are the same coroutine**: hand `StreamingResponse` a plain async generator and every database read waits for the previous socket write, so a client on a slow link keeps a server-side cursor idle for the whole download — and the obvious fix, a task and a queue, is worse, because the obvious queue is unbounded and a producer faster than its client reads the entire table into it, which is the export materialised in memory with nothing raised until the OOM kill. `with_readahead` is one owned producer task behind a queue with a maximum size, so peak memory is `EXPORT_READAHEAD_CHUNKS × EXPORT_CHUNK_BYTES` and cannot become anything else; `TestTheProblemBeingSolved` asserts both halves against `asyncio.Queue` itself. The producer is a `TaskScope` child with `WhenScopeExits.CANCEL` rather than a bare `create_task`, which here would be every problem `src/structured` documents at once. **Once the first byte is sent the status line is spent** — the handlers are inside the middleware stack and Starlette re-raises rather than renders after a response has started — so a failure at row 400,000 either cuts the connection, leaving a truncated file that arrived with a 200, or the body admits to it. Nothing in HTTP rescues that: `Content-Length` is unknowable before the last row, chunked framing terminates cleanly either way, and NDJSON truncated at any line is *valid* NDJSON, so the consumer doing the obvious thing gets a short file and no error. Every stream therefore ends with a terminal record — `{"_export":"complete","records":N}` or a `failed` one carrying an application error code from `src/exceptions.py`, the same vocabulary the JSON envelope uses before the first byte — and its absence is how a client detects truncation; buffered records are flushed ahead of a failure so the count describes the body exactly, and an unexpected exception reports `INTERNAL_ERROR` with a fixed message rather than quoting a traceback into a body that is already public. Failures *before* the first byte stay ordinary 401/403/422 envelopes, which is why the generator is lazy rather than primed. **Nothing closes an abandoned generator**: Starlette iterates the body with `async for` and never calls `aclose()`, so a client disconnect leaves the generator — and the scope, task and cursor inside it — for the garbage collector, which is not a schedule a connection pool can be sized against; each layer now closes the one below it, and the middle one was found by a test rather than by reading, because breaking out of an `async for` closes nothing. The deadline is armed around the producer *task* and never inside the source generator, since `asyncio.timeout` cancels the task it was entered in and the cancellation lands wherever that task is suspended — usually `Queue.put`, a frame the generator's own `async with` would never see — which also makes it cover time spent blocked on a client that has stopped reading, that being a hold on the cursor exactly as effective as a slow query. The query names the eight published columns rather than `select(User)`, so the password hash is never fetched at all; **that is not a memory argument, and two earlier drafts of this claim were wrong until measured** — SQLAlchemy's identity map is weak-referencing, so streamed entities are collected as they go, and asyncpg tolerates an abandoned cursor rather than failing the next statement — so `tests/test_streaming_db.py` captures the emitted SQL to assert the hash is absent, asserts the entity query it replaces *does* contain it, and checks `AsyncResult.closed` instead of a query that would pass either way. Two encoding details are not stylistic: `allow_nan=False`, because Python's `NaN`/`Infinity` are not JSON and would break a consumer's parser in the middle of a large file, and U+2028/U+2029 escaped despite `ensure_ascii=False`, because `str.splitlines()` breaks on them and a display name containing one would split a record in half. No CSV — a truncated CSV is a valid CSV with nowhere to put a terminal marker a spreadsheet would not render as one more row of data — no background export job with a download link (`EXPORT_DEADLINE_SECONDS` is where the boundary to that is written down), no resumption, and nothing yet bounds how many exports run at once, each holding a pooled connection for its duration (PR #40)
- [x] Server-Sent Events endpoint with heartbeat and client disconnect detection — `src/sse` plus `GET /api/v1/events/stream`, documented in `docs/server-sent-events.md`, 100% line coverage on all seven new modules and the route. The keepalive is the *detector*, not decoration: Starlette reads the ASGI receive channel only below spec_version 2.4, so on the servers this runs on a vanished client is discovered by a `send()` that raises — nothing polls — and a stream with nothing to say makes no writes. An idle stream whose client has gone is therefore undetectable, its generator suspended holding a hub subscription until something is published on that topic, which for a per-user topic may be never and is also what repairs it. A comment frame every `SSE_HEARTBEAT_SECONDS` makes that interval the ceiling on how long an abandoned stream holds its resources; `tests/test_sse_endpoint.py` asserts it over a real socket against a real uvicorn, because httpx's `ASGITransport` buffers the whole body and never returns for a stream that does not end. Three more things stop being true once a response never ends. The status line is spent after the first frame, so a client that falls behind is closed with an `overflow` event rather than having events dropped under it — `EventStreamHub.publish` is a plain `def` with no awaits, so one slow browser can neither stall nor fail the request that produced the event. Every connection is a lifetime, ended by *finishing* the body rather than by raising, checked between frames because `asyncio.timeout` fires wherever the consuming task happens to be. And the wire format has no escaping, so a line break inside a value is a frame boundary: CR, LF and CRLF are normalised and nothing else is (`str.splitlines()` breaks on characters SSE passes through), while empty `data` and a NUL in `id` are refused because a client answers both by silently doing nothing. No `id:` is sent and `Last-Event-ID` is not honoured: nothing stores past events to replay from, and an id would promise a resumption that is not kept (PR #41)

Known gaps carried into the rest of Phase 8: the hub reaches only the clients
connected to *this* process, so a second replica's streams do not see an event
published here — the seam for a broker is `EventStreamHub.publish`, which a
Redis or Kafka subscriber can call on each replica without any stream knowing.
There is no replay buffer, so a reconnecting client is told to refetch (`ready`)
rather than resumed. The `sse.stream_closed` line cannot be asserted through
`structlog.testing.capture_logs`: `configure_logging` sets
`cache_logger_on_first_use=True` with a filtering bound logger at `LOG_LEVEL`,
so a module's first log call caches that level filter and an `info` line is
dropped before the processors `capture_logs` swaps — which is why
`tests/test_sse_stream.py` replaces the module's logger instead. Existing log
assertions elsewhere in the suite pass only because they happen to run before
anything configures logging.
- [x] WebSocket endpoint with JWT auth, rooms, and per-connection rate limiting — `src/ws` plus `/api/v1/ws`, documented in `docs/websockets.md`, 100% line coverage on all five new modules and the route. Four things HTTP was doing for us stop at the upgrade, and each is a module rather than a function. **Authentication has nowhere to live**: a browser's `WebSocket` constructor cannot set a header, so `Authorization: Bearer` is unavailable to exactly the clients this is for, and the three ways around that are a token in the query string (written down by the access log, every proxy, browser history and `Referer` — refused here, with a test, because "it works anyway if you also send it properly" is how a rejected mechanism comes back), a first message after `accept()` (which inverts the property that makes authentication useful: the peer holds a socket and a task before proving anything, so the cheapest denial of service becomes connecting and saying nothing), and `Sec-WebSocket-Protocol`, which is what this uses — `["bearer.auth.v1", token]` is a request *header*, the tag is echoed on accept and the token never is, and a JWT is a legal subprotocol token only because base64url plus `.` happens to be. Two facts about refusing before the handshake completes were measured rather than assumed and are why the answer is a bare 403 with the reason in a log line: a close code passed before `accept()` is **discarded** (uvicorn answers HTTP 403 whatever you pass), and the ASGI 2.4 denial-response extension — which would have carried this API's usual 401 envelope — is advertised, produces the right bytes for a raw `httpx` request, and still is not usable, because uvicorn logs `ASGI callable returned without completing handshake` and the reference Python client reports `InvalidMessage: did not receive a valid HTTP response` instead of the status. **A credential now outlives its use**: a request finishes long before its token expires and a connection does not, so verifying `exp` only at the handshake grants an access that never ends — a role changed or a session revoked an hour ago is still live on a socket opened before it — and the connection carries the expiry as a deadline with its own close code (4401) because the remedy is refresh-then-reconnect rather than reconnect. `verify_access_token` moved to `src/auth/utils.py` so the two transports cannot drift on what a valid access token is. **There is no request to rate limit**: the whole connection is one request, so the per-address middleware counts it once however many messages arrive, and the replacement is per connection and deliberately does not sleep (the frames are already buffered, so sleeping in the receive loop stops draining what the sender is still filling), does not queue the overflow (a rate limit with a buffer is a memory limit), and bounds messages *and* bytes, since either alone is trivially evaded; consecutive violations, not total, disconnect. **Every peer is now a publisher**: a broadcast runs inside another client's receive loop, so `RoomRegistry.broadcast` holds the same never-blocks-never-fails invariant as the SSE hub for a sharper reason, and one outbound queue with one writer task per connection is what keeps two coroutines from interleaving frames on a socket ASGI does not make re-entrant. Also refused at the decoder: `NaN`/`Infinity`, which `json.loads` accepts and `json.dumps` will not re-emit — an asymmetry that is otherwise one sender's payload costing a whole room their connections, because it fails at the broadcast rather than at the sender. Two pre-existing bugs surfaced and were fixed: `RequestIDMiddleware` claimed to handle `websocket` scopes and could not (it built a `Request`, whose constructor asserts the scope is HTTP), so the first connection to this endpoint was a 500 the client saw as a rejected upgrade; and an overflowed connection waited for its next inbound frame to notice, which for a read-only room participant is never. A third was caught by `tests/test_cancellation_gate.py`, which rejected the pre-close flush for swallowing `CancelledError`. Not done, and written down rather than left to be found: cross-process fan-out (the seam is `broadcast`, as with `EventStreamHub.publish`), replay after reconnect, room authorisation beyond authentication, presence, and a per-account connection limit (PR #42)
